# QA notes — T6 Share a bundle from the saved list

Written for someone who **cannot read the code** and has never seen this change.

## What changed, observably

The "Saved documents" panel gained a new way to share more than one document at once.

- Open "Saved documents" (the library button in the top bar). If it has at least one document
  saved, a new **`Share`** button appears in the panel's footer, next to nothing else — the footer
  used to be empty.
- Click `Share`: every row grows a checkbox on its left, and each row's `rename`/`delete` buttons
  disappear (clicking a row now means "select it", so the old per-row buttons are hidden rather than
  competing for the same click). The footer changes to **`Cancel`** and **`Create link`**.
- `Create link` is greyed out until you tick at least one row, and while greyed out a line of text
  under the buttons says why.
- Tick exactly **one** row and click `Create link`: you get the ordinary, familiar share dialog —
  lifetime picker, "Create link" button, the resulting link and its copy button. This is unchanged
  from what sharing the currently-open document already does.
- Tick **two or more** rows and click `Create link`: you get the **same** dialog, just labelled for
  several documents (its subtitle says how many, and the total size).
- **New:** opening a link that was made from several documents no longer fails. It lands on a new
  screen — "Import shared documents" — listing every document in the link by name, size and (when
  available) its resource/type summary. Every row starts ticked, except a document whose *content*
  exactly matches one you already have saved, which is labelled "Already saved" and starts unticked.
- `Import selected` on that screen saves the ticked ones to your library and tells you how many, with
  an `Open` button next to each. `Cancel` discards the lot and returns to the paste screen.

## Where to exercise it

- **Environment:** `preview_start { name: "jsonapi-lens" }` — the dev server on port 5178.
- **Surface:** the top bar's library button (saved-documents panel) and, once a link is opened, the
  new "Import shared documents" screen.
- **Note, same as T5's:** `/api/*` is not served by the dev server, so **the actual network upload
  and download that a real share link needs cannot happen here.** You can exercise every screen and
  every button up through the point a link would be created or opened, and it should fail *readably*
  (a clear error in the share dialog, not a silent hang or a crash) rather than actually producing a
  usable link. **Do not test against production** — a real upload creates a real row in a real
  database. If you want to see the full round trip (mint a bundle, open it, see the import screen
  with real rows), that needs either a production pass or someone running `wrangler dev` locally —
  this task's own evidence file records which of those it did and did not do; please read that
  before deciding this is untested rather than "not testable here."

## How to exercise it

1. With nothing saved yet, open "Saved documents". Confirm there is **no** `Share` button — only
   whatever the panel already shows for an empty library.
2. Paste the **Article feed** sample, click **Save**, give it any name. Paste the **Single resource**
   sample, save that too, under a different name. Open "Saved documents" again: both are listed, and
   a `Share` button is now present.
3. Click `Share`. Confirm: a checkbox appears on every row; the row's own open/rename/delete controls
   are gone; the footer now reads `Cancel` and a greyed-out `Create link` with a line of text
   explaining why it is greyed out.
4. Tick one checkbox. `Create link` becomes clickable. Untick it again — `Create link` greys out
   again, and the explanatory text comes back.
5. With one box ticked, click `Create link`. Confirm the familiar share dialog opens (lifetime
   choices, a `Create link` button inside it). Its subtitle should show the one document's name and
   size. Clicking its `Create link` should fail with a readable network error (see the note above) —
   that failure is expected here, not a defect.
6. Reopen "Saved documents", click `Share`, tick **both** rows, click `Create link`. Confirm the same
   dialog opens, but its subtitle now names the count of documents (e.g. "2 documents") and a total
   size, rather than one filename.
7. Back in selection mode (tick at least one box first, so there is something to lose): press
   **Escape** once. Confirm the panel returns to its normal list (checkboxes gone, rename/delete
   back), **and the "Saved documents" dialog is still open.** Press **Escape** a second time: now the
   dialog closes.
8. Reopen "Saved documents", click `Share`, tick a box, then click `Cancel` (not Escape). Confirm the
   same thing as step 7's first Escape: back to the normal list, dialog still open. Click `Share`
   again and confirm the box you ticked before is **not** ticked any more — the selection was
   genuinely discarded, not just hidden.
9. Save a document whose name you type as `<img src=x onerror=alert(1)>` (paste any sample first,
   then use that as the name when saving). Open "Saved documents" and click `Share`. Confirm that
   exact text appears as the row's visible name — as plain text, not as a broken image icon and
   definitely not as a JavaScript alert popping up.
10. If you have a way to reach the import screen (see the note above — this needs a real link, so it
    is likely only reachable via this task's evidence file's recorded steps, or a production pass):
    confirm every row starts ticked except one whose content you already have saved elsewhere, which
    should start unticked and say "Already saved". Confirm resizing the browser to 375px wide never
    produces a horizontal scrollbar on the page, even with many rows.

## Test data needed

The built-in samples (Article feed, Single resource) are enough for everything except the actual
network round trip. For the hostile-label check in step 9, the exact string is:

```
<img src=x onerror=alert(1)>
```

## What should NOT have changed

- Sharing the **currently open** document (the `Share link` button in the document's own overview,
  not the library panel) looks and behaves exactly as before — same dialog, same fields.
- Back and Forward return the content you were looking at to the same place on screen, for the
  ordinary document view. This task's own new views (paste, and the new import screen) should also
  be reachable via Back and Forward after a bundle link loads — see the browser scenario recorded in
  `docs/evidence/T6.md`.
- Nothing in the network log carries document content in the clear — the one new thing this task can
  upload is still ciphertext, through the same `/api/shares` endpoint as before.
- Renaming and deleting a saved document, outside of selection mode, works exactly as before.

## Known limitations

- **A real bundle link has not been exercised end to end against production for this task** — see
  `docs/evidence/T6.md`'s NOT OBSERVED section for exactly what was and was not verified locally with
  the network call intercepted. Treat "the import screen renders and imports correctly" as verified
  against a locally-constructed bundle, and "a real upload/download of a bundle through the live
  Worker" as **not yet verified by anyone**, the same open item T5's QA notes left behind.
- **Redaction is not part of this task** — there is no such feature anywhere in this codebase yet
  (it is T2's). If you notice no redaction offer when sharing a document with an attached
  request/response, that is expected, not a gap in this task.
- **A bundle entry that is not valid JSON** is not caught at import time — it imports like any other
  document, and only shows an error if you later try to open it. This is deliberate (see the task
  spec); do not file it as a defect that "Import selected" does not validate content.
