# QA notes — T7 MCP server — share and read

Written for someone who **cannot read the code** and has never seen this change.

**This task has no browser surface of its own.** It adds `mcp/`, a small program that speaks a
protocol called MCP over its stdin/stdout — an AI assistant's tool-calling mechanism, not something
with a page, a button, or a URL you visit directly. There is nothing to click, and no new screen in
`jsonapi-lens` itself changed. The one place this task's work becomes visible in a browser is
downstream of it entirely: **a share link this server mints has to open exactly the way a share link
minted by the app's own Share button does**, because both are sealed by the exact same code
(`src/crypto.ts`) — that is the whole point of this task, stated in its own spec as "one crypto
implementation, never two."

So your job here is narrower than usual, and it is exactly the thing you already know how to check:
**does a link produced by this server render correctly**, the same way you would verify any other
share link.

## Where to exercise it

- **You will be given a URL** — `https://jsonapi.mstool.dev/d/<id>:<secret>` — that the implementer's
  evidence file (`docs/evidence/T7.md`) recorded producing with this server, via a real terminal run,
  against production, with a synthetic document and the shortest lifetime (15 minutes). If that link
  has since expired (15 minutes is short) or you were not handed one, say so and ask for a fresh one
  rather than trying to mint your own — you have no MCP client to call `share` with, and that is
  expected; see "Known limitations."
- **Surface:** whatever page that URL opens — the document view, or (if the implementer shared
  several documents at once) a bundle prompt. This is the same `/d/<id>:<secret>` route every other
  share link uses; nothing about the route is new.

## How to exercise it

1. Open the URL you were given, in a real browser, in each of the three languages (`?lang=en`,
   `?lang=de`, `?lang=uk`, or use the language switcher after it loads).
2. Confirm it renders the document — for a single document, the document view with its content
   visible and correct; for a bundle, whatever the current build offers for a multi-document link
   (as of this task, T6's bundle-import view may not exist yet — if the link instead shows the
   existing "this link was made by a newer version" or an unrelated error, check
   `docs/evidence/T7.md`'s account of what it observed before treating that as a defect).
3. Confirm the address bar no longer shows the secret after the page finishes loading — the app
   strips it from history the same way it does for any share link, and this task changes nothing
   about that behaviour.
4. Confirm the usual things any page render should get right: no console errors, no network request
   after the initial fetch carries anything resembling the document's content in plaintext (only the
   single `GET /api/shares/<id>` for the encrypted blob), and the layout is not broken at 375px wide.

## Test data needed

None to construct yourself — the document behind the link you are given is synthetic, created for
this purpose (per `docs/DELIVERY.md`'s rule against uploading anything else to production). You do
not need to know what it says; you only need to confirm it renders.

## What should NOT have changed

- **Every other way of creating or opening a share link is untouched.** The Share button, the
  lifetime picker, the copy-link flow, and opening a link minted by the Share button all behave
  exactly as before — this task added a second way to reach the same envelope format, not a new
  format.
- Back and Forward return the content you were looking at to the same place on screen.
- A row that was expanded is still expanded, and still expands when clicked.
- Nothing in the network log carries document content in plaintext.
- No user-facing string anywhere in `jsonapi-lens` itself changed — this task's own text (tool
  descriptions, refusal messages) is read by an AI assistant calling the MCP server, never rendered
  in the app, and is deliberately not part of the `en`/`de`/`uk` catalogues for that reason. Do not
  go looking for new strings in the UI; there are none.

## Known limitations

- **You cannot independently mint a link for this task.** Doing so needs an MCP client (or a
  hand-rolled JSON-RPC session over stdio), which is outside what a browser-driving QA pass has, and
  outside what this task's process profile (`docs/DELIVERY.md`: `qa-surfaces: web`) covers — there is
  no `qa-api`-equivalent role for this. You are verifying the one link the implementer's evidence
  file already produced, the same way you would sanity-check any other piece of evidence.
- **The MCP protocol layer itself — tool registration, the exact wording of refusals, the
  cross-compatibility guarantee between this server and the browser's own `seal`/`open` — is not
  something a browser pass can observe at all.** It is covered by `mcp/`'s own automated test suite
  (`test/mcp/`), including one test that spawns the real server as a subprocess and checks its actual
  stdout/stderr never contain a secret. If you have no way to run that suite yourself, take its
  existence and the test plan's description of it as the record, the same way you would treat any
  other test file you are not asked to re-derive.
- **If T6's bundle-import view does not exist yet on this build**, a bundle link (several documents
  behind one URL) will not render as a multi-document import screen — see step 2 above. That is not
  a defect in this task; T7 mints the link, T6 owns the view that displays a bundle's contents.
