# QA notes — T5 Storage and share envelope

Written for someone who **cannot read the code** and has never seen this change.

**This task has no UI, on purpose.** It changes what can be stored and what a share link can carry,
so that three later tasks (T2's request model, T6's "share several documents", T7's MCP server) can
be built on top of it without waiting on each other. There is no new screen, button, or visible
control to click. Your job for this task is almost entirely a **regression check**: confirm that
paste, save, the saved-documents library, and share links still work exactly as they did before —
because all of them now sit on top of a storage layer and a share envelope that quietly gained the
capacity to hold more, without changing what they do today.

## What changed, observably

Nothing new to look at. What you are checking is that nothing **broke**:

- A document you paste and save still saves, lists, opens, renames and deletes from "Saved
  documents" exactly as before.
- A share link you create still creates, copies, and opens exactly as before.
- If you open your browser's DevTools → Application → IndexedDB → `jsonapi-lens`, the database
  version now reads **3** (it was 2). This is the one directly-observable trace of this task. It
  does not require you to know what "version 3" means — only that opening it does not show an error,
  and the `documents`/`library` stores are still there with your data in them.

## Where to exercise it

- **Environment:** `preview_start { name: "jsonapi-lens" }` — the dev server on port 5178.
- **Surface:** the paste view, the document view's Save button, the "Saved documents" panel, and the
  Share button/modal. All exist already; none of their controls changed.
- **Note:** `/api/*` is not served by the dev server, so **share links cannot be created or opened
  against the dev server** — creating one will fail with a network error, which is expected and not
  a defect. Do not test share against production either: uploading a real share creates a real row in
  a real database with a real lifetime, and this task does not need that to be exercised to be
  verified. If you want to see a share link work end to end, that is what the implementer's evidence
  file (`docs/evidence/T5.md`) already did once, against a throwaway build, and it is not something
  this QA pass should repeat against the live site.

## How to exercise it

1. Paste one of the built-in samples (Article feed is fine). Click **Save**, give it a name. Open
   "Saved documents" and confirm it lists, with the same shape/resource/type summary it always showed
   (e.g. `data[2]` · 6 resources · 3 types).
2. Rename it, confirm the new name sticks. Delete it, confirm it is gone.
3. Paste a document, click **Share**, pick any lifetime, click **Create link** — confirm this fails
   with a clear network error (dev server has no `/api/*`), not a silent hang or a confusing crash.
   This is the one place the dev server's limitation is expected to show up, and it should still fail
   *readably*.
4. Open DevTools → Application → IndexedDB → `jsonapi-lens` and confirm the version reads 3 and both
   stores (`documents`, `library`) are present and browsable.
5. Reload the page with a document open (or one saved from step 1 still in the library) and confirm
   both are still there after the reload — this is the "a v2 record still opens under v3" guarantee,
   observed the only way a browser pass can observe it: nothing was lost.

## Test data needed

Any built-in sample works for this — Article feed is the default and is fine. Nothing about this
task depends on a specific payload shape; the point is that ordinary use of the existing Save/Share/
Library features is undisturbed.

## What should NOT have changed

- Back and Forward return the content you were looking at to the same place on screen. (This task
  touches no render path, so this should be trivially true — worth a quick check anyway, since it is
  the regression this codebase has shipped before.)
- A row that was expanded is still expanded, and still expands when clicked.
- Nothing in the network log carries document content — the only request `/api/shares` ever receives
  is ciphertext, exactly as before.
- The Save/Share modals look and behave identically to before — same fields, same copy, same buttons.
  If anything in either modal looks different, that is a defect: this task promises not to touch UI.

## Known limitations

- **Share links cannot be exercised in this environment at all** — not locally (no `/api/*` on the
  dev server) and not safely against production (would upload real ciphertext). The implementer's
  evidence file records one real share round trip performed once, deliberately, against a disposable
  build; this QA pass should not repeat it.
- **The actual cross-version migration** — a document saved by the previous build, loaded by this
  one, in a real browser rather than a simulated IndexedDB — is exactly what
  `docs/evidence/T5.md` exists to record, because it is the one thing in this task that unit tests
  cannot prove by themselves. If that file's account of it looks incomplete or you cannot reproduce
  the before/after browser state yourself, say so — that is a legitimate QA finding, not something to
  wave through.
- **Bundles (several documents behind one link) are not observable at all in this build.** They are
  fully implemented underneath, but there is nowhere in the UI to create or open one yet — that is
  T6. Do not go looking for a way to select multiple documents to share; there isn't one, and that is
  correct for this task.
