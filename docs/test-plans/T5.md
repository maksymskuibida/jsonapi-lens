# Test plan — T5 Storage and share envelope

**What this task changes, in one paragraph.** A stored document (current or in the library) can now
carry an optional `exchange`; IndexedDB moves to `DB_VERSION` 3 to record that, additively; and the
share envelope gains a second payload — a **bundle** of several documents — sealed at a new envelope
version (3), while a single-document share stays version 2 forever. None of this has a UI: T2, T6 and
T7 build on it. The headline constraint is backward compatibility in both directions — every document
already saved, and every share link already sent, keeps working exactly as it does today.

## Scope

- **In scope:** `src/store.ts` (the `DB_VERSION` bump, `StoredDocument`/`LibraryEntry` widened with
  `exchange`, and `LibraryEntry`'s `resources`/`types`/`shape` made optional), `src/crypto.ts` (the
  envelope: `BundlePayload`/`BundleEntry`, `sealBundle`, the widened `open`, the secret-length bound),
  `src/share.ts` (`fetchShare`'s narrowed contract while there is no bundle view yet), `src/exchange.ts`
  (the `Exchange` placeholder), and the `bundle` i18n catalogue.
- **Out of scope:** Any UI for selecting, creating or importing a bundle — T6. The `Exchange` model's
  real shape — T2. The MCP server — T7. Any change to the Worker, `migrations/`, `router.ts`, the KDF,
  the cipher, the compression, or the version-2 payload's existing fields — covered instead by the
  compatibility fixture and the "what should NOT have changed" section below.

**Altitude matters more than count here.** Nothing in this task is measured in pixels — there is no
UI — so every case above is a `vitest` case under `test/`, in `test/store.test.ts` and
`test/crypto.test.ts`. There is no `test/browser/nav-scenarios.js` addition, because there is nothing
to lay out. The one thing genuinely outside `vitest`'s reach is case 5 (a cross-tab IndexedDB
upgrade) and the real migration itself (a document saved by yesterday's deployed build, loaded by
today's) — `fake-indexeddb` proves the *shape* tolerance, but not that an actual browser upgrades an
actual on-disk database cleanly. That is what `docs/evidence/T5.md`'s browser pass is for, and it is
the one thing in this plan marked for a human/browser check rather than `vitest`.

**Do not mark a row "automated" unless the test genuinely exists.** Every "automated (vitest)" row
above has a corresponding `it()` in `test/store.test.ts` or `test/crypto.test.ts`, and each was
verified capable of failing by temporarily reverting the code it guards (self-review, not asserted
here as a claim — see the PR body for which mutations were tried).

## Edge cases enumerated

**Payload shape (share envelope)**

- Empty bundle; a bundle entry with empty text; a bundle entry whose text is malformed JSON (carried,
  not validated); a bundle entry whose `label` contains markup or emoji (not this task's problem to
  render — T6 — but confirmed it round-trips through `seal`/`open` unescaped, since neither module
  renders anything at all).
- A duplicate label across two bundle entries (kept, not deduplicated).
- A secret of 7, 8, 64 and 65 characters, and the existing generated 10-character secret.
- A version byte of 2, 3, and neither (4, 99).

**Identity and anchors** — not applicable. This task mints no DOM ids and touches no anchor.

**Injection** — not applicable to `crypto.ts`/`store.ts`/`share.ts` directly: neither module builds or
assigns raw markup to the page. `panels.ts`'s two-line fix (tolerating an absent `resources`/`types`)
touches only `el(..., { text: … })`, which is a `textContent` assignment, not markup — confirmed by
reading `src/dom.ts`'s `el()`. A hostile `BundleEntry.label` is exercised in the tests above only for
byte-for-byte round-tripping through the envelope; rendering it safely is T6's job when it builds the
bundle import view, and its own test plan should repeat this check against its actual render path.

**Scale and layout** — not applicable (no UI). The one scale case in scope is the 12 MB bundle cap
(#16) and the 5 MB single-line entry (#15), both automated.

**Localisation**

- Every new string (`bundle.errors.*`) present in `en`, `de` and `uk` — enforced by `tsc` alone:
  `Messages` is derived from `en`, so a missing `de`/`uk` key, or a function whose parameters drifted,
  fails typecheck. `test/i18n.test.ts` does not walk the catalogue generically; its checks are each
  targeted at a specific existing surface (the locale switcher, plural forms in specific messages, the
  static legal-page markup) and none of them reach the new `bundle` namespace. Catalogue parity here is
  compile-time only.
- No English literal in a template; no `??` fallback — self-reviewed by reading every new string in
  `crypto.ts`.
- Ukrainian's four plural forms used correctly for the secret-length count (`символ`/`символи`/
  `символів`/`символу`), matching the existing convention elsewhere in `uk.ts`.

**Persistence and the privacy promise**

- Reload with a document open: comes back from IndexedDB, with or without an `exchange` (#1, #3).
- Storage blocked or unavailable: every `store.ts` call still resolves to its safe value (#6).
- **No network request carries payload content.** `crypto.ts` never calls `fetch` (#26, enforced by a
  spy). `store.ts` never calls `fetch` (true by inspection — it imports nothing network-capable).
  `share.ts`'s `fetchShare` is unchanged in what it sends; it only narrows what it accepts back.

## What should NOT have changed

- **A single-document share stays version 2, byte for byte, whether or not it carries an `exchange`.**
  Verified directly (#8 asserts the version byte). No existing share link's meaning changes.
- **The Worker, `migrations/0001_shares.sql`, and `src/router.ts` are untouched.** Confirmed by `git
  diff` against `main` touching none of `src/worker.ts`, `migrations/`, or `src/router.ts`. The Worker
  still cannot tell a bundle from a document — it never decrypts anything.
- **The KDF, the cipher, the compression, and every version-2 field's meaning are unchanged.**
  `KDF_ITERATIONS`, `SALT_BYTES`, `IV_BYTES`, the PBKDF2/AES-GCM parameters, and gzip are byte-for-byte
  what they were — the compatibility fixture (#7) is what actually proves this, since it is decrypted
  with today's `deriveKey`/`open` against ciphertext produced by yesterday's `seal`.
- **Every existing `crypto.test.ts` case still passes unmodified** — the secret-generation,
  base64url, and original seal/open/tamper/version-mismatch tests are untouched in this diff and all
  still pass, which is what shows the widening did not disturb the version-2 path.
- **`panels.ts`'s library row layout is otherwise unchanged.** Only the two lines reading
  `entry.resources`/`entry.types` were touched, to skip rendering when absent; the shape code, the
  byte count, the relative-time string, and every button are untouched.
