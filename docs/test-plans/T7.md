# Test plan — T7 MCP server — share and read

**What this task changes, in one paragraph.** A new `mcp/` tree adds a stdio MCP server with two
tools, `share` and `read`, so an assistant can put a document — or several — behind a
jsonapi-lens share link and read one back, without a browser. It imports `src/crypto.ts` unmodified
— the same `seal`/`sealBundle`/`open` the browser calls — and talks to the same public
`/api/shares` surface `src/share.ts` already does, over `fetch` rather than from a tab. Nothing
under `src/` changes.

## Scope

- **In scope:** `mcp/server.ts` (the stdio entry point, the Node-version check, forcing the locale
  to English), `mcp/build-server.ts` (the two registered tools, their descriptions, input/output
  schemas and handlers), `mcp/validate.ts` (secret/lifetime/origin/document validation),
  `mcp/transport.ts` (the one module that calls `fetch`, and its same-origin redirect guard),
  `mcp/runtime.ts` (the Node/WebCrypto/CompressionStream capability check), `mcp/locale.ts`.
- **Out of scope:** Any change to `src/crypto.ts`, `src/share.ts`, `src/router.ts`, the Worker, D1
  or the envelope format — those are T5's, unmodified here. Reading a document from disk or a URL.
  Parsing, indexing or validating a document's contents — `read` returns text, verbatim. Deleting,
  revoking or listing shares. Generating a secret — the caller supplies one.

**Altitude matters more than count here.** There is no UI and nothing measured in pixels, so every
case above is a `vitest` case under `test/mcp/`, running in plain Node (`// @vitest-environment
node`, matching `test/crypto.test.ts`'s own convention) rather than jsdom — this tree never runs in
a browser, so testing it under jsdom would prove nothing about what actually ships. `npm run dev`
does not serve `/api/*` at all, so there is no local browser surface for this task to exercise, and
`docs/evidence/T7.md` is a real end-to-end run instead of a browser pass.

**Do not mark a row "automated" unless the test genuinely exists.** Every row above has a
corresponding `it()` in `test/mcp/`. Each was confirmed capable of failing, by actually breaking the
thing it guards and watching it go red, then reverting:

- The two size-cap tests (17-18) originally passed for the wrong reason — a `Math.random()`-based
  filler over a 90-symbol alphabet compressed enough under gzip's Huffman stage to slip back under
  the cap, so the "refusal" never actually fired — until the generator was replaced with the same
  high-entropy filler and the same 18 MB margin `test/crypto.test.ts` already uses for the
  equivalent case.
- Row 29's raw-stdio test was mutation-tested directly against a planted leak in the `share`
  handler, once with `console.log(secret)` and once with `console.error(secret)` — both produced a
  visible failure (the first on the stdout assertion, the second on stderr), and the raw captured
  text in the failure output showed the literal secret in the planted line. This replaces an earlier
  version of this test that used the SDK's own `Client`/`StdioClientTransport`, which does not
  expose the child's raw stdout at all — a review caught that the earlier version's own
  "mutation-tested" claim did not reproduce, because the SDK-parsed check it made could not have
  seen a leak written through anything other than a JSON-RPC response.
- Rows 31-32's locale-pin tests were mutation-tested by removing `mcp/build-server.ts`'s
  `import "./locale.js"` (all three locale rows failed, showing real German/Ukrainian text) and,
  separately, by disabling the unconditional `localStorage.setItem` call in `mcp/locale.ts` (the
  same three rows failed again, including row 31, confirming the fix genuinely depends on that
  write rather than on the stand-in's mere installation).

## Edge cases enumerated

**Payload shape**

- Empty `documents`; one document; several documents; a document with empty `text`; one of several
  with empty `text`.
- A document `label` containing markup, quotes or emoji — carried and returned verbatim, since
  neither `mcp/` nor `crypto.ts` renders anything. (Rendering a bundle's contents safely is T6's
  responsibility when it builds that view, and its own test plan should repeat the injection check
  against its actual render path.)
- A document whose `text` is not valid JSON — carried and returned as-is; this tool does not parse.
- An `exchange` object attached to a document, and one omitted — both round-trip correctly through
  `share` then `read`.

**Secrets**

`share` and `read` are answering different questions about a secret, and this task's first review
round caught that treating them as the same question was itself the defect: a single shared check
insisting on 64 lowercase hex meant `read` refused every link the browser has ever minted. The fix
keeps two separate functions in `mcp/validate.ts`, one per tool, both refusing rather than
normalising:

- `assertShareSecret` (mints): 64 lowercase hex accepted; 63 and 65 refused (the bound named);
  non-hex characters at 64 length refused; empty string refused; uppercase and mixed-case hex
  refused. Message names the exact expectation and `openssl rand -hex 32`.
- `assertReadSecret` (opens): anything `crypto.ts`'s own `[MIN_SECRET_CHARS, MAX_SECRET_CHARS]` of
  `[A-Za-z0-9_-]` accepts — a real `generateSecret()` output, uppercase or mixed-case hex, the T5
  fixture's own 10-character secret, the exact boundary lengths 8 and 64 — is accepted, case
  preserved exactly (never folded). Only too short, too long, or outside that alphabet is refused,
  and the message says "malformed or truncated", naming the 8-64 bound, **never** the `openssl`
  command — there is nothing to generate on a path where the caller does not get to choose the
  secret.
- A secret `assertShareSecret` accepts always passes `assertReadSecret` too, by construction (64
  lowercase hex is a subset of the wider range), so `share` immediately followed by `read` on the
  same secret can never disagree with itself — asserted directly, not just argued in a comment.
- Neither function ever echoes the invalid secret's own characters back — only its length, matching
  `crypto.ts`'s own convention for its (differently-bounded) length check.
- The T5 fixture's secret (`fixtureT5x`, 10 characters) now flows through the registered `read` tool
  end to end, not only through `open()` directly — see case 7.

**Lifetime and origin**

- All six accepted lifetime keys; a seventh, invented one; the default when omitted.
- The default origin; an explicit `http://` origin (for a self-hosted fork); a path; a query string;
  a fragment; a non-URL string; a non-http(s) scheme.
- **Userinfo** (`https://jsonapi.mstool.dev@evil.example.com`, with and without a password): refused,
  naming the host the upload would actually reach. `new URL(origin).origin` silently discards
  userinfo, so this string's `.origin` is `https://evil.example.com` even though the part a human (or a
  model) reads as the host is `jsonapi.mstool.dev` — the sharpest form of "looks right, uploads
  elsewhere" this function exists to catch, and the one review escalated from suggestion to blocker:
  this is the sole component in the release that decides which network destination receives a
  document, so it is the one place a plausible-looking wrong host actually matters, and the caller
  reading the tool call is not necessarily the person who typed the origin — it can be text a model
  read somewhere else.
- A response whose final URL, after a redirect, does not match the requested origin — refused before
  the body is read, so a malicious or misconfigured origin cannot smuggle a response from somewhere
  else in under a matching status code. Every real network call also passes `redirect: "error"`, so
  on a genuine `fetch` a redirect anywhere — same host or not — rejects before a response exists to
  inspect; the origin check remains as a backstop for a test double or any future non-`fetch`
  `fetchImpl`, which is not bound by `redirect` at all.

**Locale**

- `mcp/build-server.ts`'s `createMcpServer`, used directly without going through `mcp/server.ts`
  (the shape `docs/test-plans/T7.md` itself documents building, and the shape a test uses), still
  answers in English under a German or Ukrainian host `LANG`/`LC_ALL` — case 31.
- The same, with a working `localStorage` already installed before the pin runs (simulating
  `--experimental-webstorage` or a host-supplied polyfill) — case 32. An earlier version of the pin
  skipped installing anything in this situation, because it treated "does a storage exist" and "is
  our key set in it" as the same question.

**Size**

- A single document and a bundle each just over the 12 MB ciphertext cap — refused, naming the
  offending document(s) and the overage, before any upload is attempted.
- A ~18 MB high-entropy document that still lands comfortably over the cap after gzip — the margin
  this suite settled on after the first version's tighter margin passed for the wrong reason (see
  above).

**Errors and the no-oracle rule**

- 404, 410, and a non-2xx create response (with the server's own error text and status) each produce
  a distinct, readable message — except the pair that must be *indistinguishable on purpose*: a
  wrong secret and a tampered ciphertext, asserted byte-for-byte identical.
- A version byte the reader does not know, naming both numbers.
- A network failure (the injected `fetchImpl` itself throwing) surfaces readably rather than as an
  unhandled rejection.

**Secrecy**

- Across a full `share` + `read` cycle, including a deliberate wrong-secret attempt, nothing passed
  to `console.log`/`info`/`warn`/`error` contains either secret used.
- `share`'s own structured result carries the secret only inside `url`; every other field, and the
  human-readable `content` text, is checked not to contain it — this is why the `content` text does
  not repeat the URL the way an early draft of the handler did.
- The one subprocess-based test (case 29) checks the same property against the real entry point and
  **the real, raw stdout and stderr byte streams** the child process actually writes — not the
  SDK client's parsed results, which is what an earlier version of this test checked and which
  cannot see a leak written any other way (`console.log`, `console.error`, or a future dependency
  writing to `process.stdout`/`process.stderr` directly).

**Runtime**

- Node at, above, and one major below the minimum (22); missing `crypto.subtle`; missing
  `CompressionStream`; both missing at once; an unparseable version string — every branch of
  `runtimeProblem`, a pure function, so none of this needs an actually-old Node to test.

**Registered tool descriptions**

- `share`'s description contains the `openssl rand -hex 32` command, the `<origin>/d/<id>:<secret>`
  pattern, and states plainly that the secret is unrecoverable from the id and that the link (not
  the id) grants access — read from `client.listTools()`, the same thing a calling model would see,
  not from this module's source comments.

## What should NOT have changed

- **`src/` is untouched.** `npx vite build`'s output (bundle names, sizes) is unchanged from before
  this task, confirming nothing in `mcp/` leaked into the browser bundle — there is no import path
  from `src/` into `mcp/` in either direction beyond `mcp/` importing `src/crypto.ts`,
  `src/format.ts` and `src/exchange.ts` (and, transitively, `src/i18n/*` and `src/dom.ts` for
  typechecking only — see `mcp/tsconfig.json`'s header comment).
- **The Worker, `migrations/`, and `src/router.ts` are untouched.** This task adds no endpoint, no
  D1 column and no route; `mcp/transport.ts` calls the two routes that already exist.
- **Every existing `test/crypto.test.ts` case still passes unmodified**, and `npm test`'s full count
  only grows by this task's own new files under `test/mcp/`.
