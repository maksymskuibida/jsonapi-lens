# Test plan — T9 The preflight flags its own test fixtures

**What this task changes.** `scripts/review-preflight.sh`'s code invariants (innerHTML,
href, network-call, DOM-id, hardcoded-copy, jsdom-altitude) now read only the files each one
actually governs — an inclusion pathspec on `src/` or `test/` (excluding `test/browser/`) — instead
of every added line in the whole diff. The two hygiene checks that are genuinely about any file
(conflict markers, focused/skipped tests) instead exempt `scripts/attack-preflight.sh` by its exact
path. `BASE_REF` is resolved (PR base → this branch's upstream → `origin/main`) instead of hardcoded,
failing closed if none resolve. `.github/workflows/deploy.yml`'s `pull_request` trigger no longer
filters on the PR's base branch, so `check` runs on a pull request stacked on a feature branch, not
only one opened directly against `main`.

This is a tooling change with no application surface: no UI, no user-facing behaviour, nothing a
browser session could exercise. The only "user" of this change is the reviewer role and CI itself, so
this plan's cases are what `scripts/attack-preflight.sh` asserts, not a browser scenario.

## Scope

- **In scope:** the six code-invariant scans' file scoping; the two hygiene checks' attack-suite
  exemption; `BASE_REF` resolution order and its fail-closed behaviour; the `pull_request` trigger's
  branch filter in `deploy.yml`.
- **Out of scope, and where it is covered instead:** which *patterns* any check searches for (none
  changed — see `docs/task-specs/T9.md` "Out of scope"); the evidence-staleness, git-ignored-file and
  required-artifact checks (unaffected, they do not read added lines); `deploy`'s job graph and the
  `concurrency` expression (unaffected by the trigger fix — verified below, not exercised by a new
  case because neither one changed); everything under `src/`, `test/`, `index.html`, `migrations/`
  (this task touches none of it — the standard app test plan sections below on injection,
  localisation, persistence and layout do not apply and are omitted rather than filled in with "N/A"
  rows, per the template's instruction to delete what genuinely does not apply).

`docs/task-specs/T9.md` "Error and edge cases", reproduced here with how each is actually verified —
every row is automated, because a gate's own test suite is exactly the place hand-verification would
be the weaker method, not a substitute for it.

## Edge cases enumerated

The template's standard sections — payload shape, identity and anchors, injection, scale and layout,
localisation, persistence and the privacy promise — all describe **application behaviour behind a
browser**. This task has none: it does not touch `src/`, does not render anything, and ships no
user-facing string. Each of those sections is genuinely inapplicable and is omitted rather than
padded with "N/A" rows.

The one item worth naming explicitly because it looks like it belongs above and does not: this task
does not touch any DOM id, JSON Pointer, i18n catalogue, or render path, so there is no injection
surface, no anchor scope, and nothing to translate. The "hostile value through a render path" case
from the standard template is not applicable — the closest analogue here is a *hostile diff*, and
that is exactly what `scripts/attack-preflight.sh` exists to throw at the gate, case by case, above.

## What should NOT have changed

- **Which patterns any check searches for.** Every regex in `scripts/review-preflight.sh` is
  byte-for-byte the same as before this task; only the input each is given changed. Verified by all
  26 pre-existing `scripts/attack-preflight.sh` cases passing unmodified — including "fails closed:
  no changes vs base" and "fails closed: base ref missing", which now also exercise the new
  resolution chain's fallback path (PR base → upstream → `origin/main`) rather than the old
  hardcoded constant, and still pass for the same reason: with no PR number and no upstream
  configured in the fixture repos, the chain still bottoms out at `origin/main`.
- **`deploy`'s job graph.** `needs: check` and `if: github.event_name != 'pull_request'` are
  untouched; `deploy` remains unreachable from any pull-request-triggered run. Verified by hand and
  by `actionlint`.
- **The `concurrency` block.** Neither the `group` expression nor `cancel-in-progress` changed.
  Verified by hand: both key on `github.event_name`, which the trigger fix does not touch.
- **The evidence-staleness check, the git-ignored-file check, and the required-artifact checks.**
  None of them read added lines, so none could be affected by this task; unmodified in the diff.
- **`scripts/attack-preflight.sh`'s existing 26 cases' behaviour.** Re-run against the fixed gate:
  still 26/26 (now folded into the full 41/41 total). Re-run against a gate stubbed dead: still all
  fail — verified together with the 15 new cases in one dead-gate pass, not separately.
