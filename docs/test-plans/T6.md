# Test plan — T6 Share a bundle from the saved list

**What this task changes, in one paragraph.** The saved-documents library gains a selection mode:
press `Share`, tick one or more rows, and `Create link` hands the selection to the existing share
modal — one document mints today's version-2 link, several mint a version-3 bundle (T5's envelope).
Opening a bundle link no longer fails; it lands on a new import view listing every document in the
bundle, ticked by default except anything byte-identical to something already saved, and `Import
selected` writes the ticked ones to the library. No change to the envelope, the payload shapes, the
Worker, or any route — T5 owns those and this task does not touch them.

## Scope

- **In scope:** `src/panels.ts` (`openLibraryModal`'s selection mode), `src/bundle.ts` (new —
  minting the right envelope version, selection resolution, duplicate detection, the import view),
  `src/share.ts` (`openShareModal` gains an optional `exchange` parameter and its modal chrome is
  factored out into `runShareModal` so `openBundleShareModal` reuses it; `fetchShare` no longer
  narrows away a bundle), `src/main.ts` (the two-place hook: a `bundle` `showView` case and the
  branch in `loadSharedDocument`/`applyRoute` that dispatches to the import view), the new
  `bundleUi` i18n namespace, and the CSS for selection rows and the import view.
- **Out of scope:** Anything T5 owns (the envelope, `BundlePayload`/`BundleEntry`, the 12 MB cap
  itself, the secret-length bound) — covered by `test/crypto.test.ts` already and re-used, not
  re-tested, here. Sharing the currently-open document via the existing overview button — unchanged
  behaviour, confirmed by the "what should NOT have changed" section. `Exchange`'s real shape — T2.
  The MCP server — T7. Redaction — not yet built anywhere in this codebase (T2), so there is nothing
  bundle-specific to verify beyond the fact that `runShareModal` is handed the whole selection before
  sealing, which is what would let a future redaction step see all of it at once.

**Altitude matters more than count here.** Nothing above measures a pixel except #27 and #29's
"page body never scrolls sideways" half, both manual/browser — `test/panels.test.ts` and
`test/bundle-view.test.ts` run under jsdom and assert DOM structure, `disabled`, `textContent` and
`checked`, never a scroll position or a `getBoundingClientRect`. `test/bundle.test.ts` runs under
Node (matching `crypto.test.ts`'s own precedent) for the parts that touch `seal`/`sealBundle`
directly.

**Do not mark a row "automated" unless the test genuinely exists.** Every "automated (vitest)" row
above has a corresponding `it()` in `test/bundle.test.ts`, `test/bundle-view.test.ts` or
`test/panels.test.ts`, and each was confirmed capable of failing during self-review (see the PR body
for the specific mutations tried — the disabled-state check, the duplicate-detection direction, and
the escape-order guard were each flipped and watched go red).

## Edge cases enumerated

**Payload shape** — not applicable in the way the template means it (this task reads no JSON:API
document); the analogous shape space here is the bundle's own: a 0-entry selection (never reaches
`mintShareEnvelope` — the button is disabled), a 1-entry selection (version 2), an N-entry selection,
and a bundle entry whose `resources`/`types`/`shape` are all absent (a v2/plain-JSON entry) — rendered
without those stats rather than as `0`, matching `panels.ts`'s existing convention for library rows.

**Identity and anchors** — not applicable. This task mints no DOM id (`bundleImportEl` has none) and
adds no anchor.

**Injection — on every task that renders anything**

- A hostile label (`<img src=x onerror=alert(1)>`) painted through both new render paths: the
  library's selection row (#13) and the bundle import view's row, before and after import (#18).
  Both use `el(..., { text })` — a `textContent` assignment — never `innerHTML`; confirmed by reading
  `src/bundle.ts` and the changed parts of `src/panels.ts`, and by the tests actually asserting no
  `<img>` element exists rather than only that the text renders.
- No URL is rendered as a link anywhere in this task's surface, so the scheme-allowlist concern
  (`javascript:`/`data:`) does not apply — the only links this task's views contain are the share
  link itself, built by the existing, unchanged `shareUrl()`/`share__url` `<input>` (a text field, not
  an anchor).

**Scale and layout**

- 50 documents in one bundle (#27): the import list is capped (`max-height: min(58dvh, 34rem)`) and
  scrolls internally, the same way the library modal's own body already does for a long list.
- No new `content-visibility` region and no change to the document view's own scroll model — the
  import view is a sibling of `.paste`/`.doc`/`.legal-view`, not layered above or beside them.

**Localisation**

- Every new string lives under a new `bundleUi` top-level key in `en`/`de`/`uk`, deliberately
  separate from T5's `bundle` key so the two diffs do not touch the same lines. Enforced by `tsc`:
  `Messages` is derived from `en`.
- The one message needing more than `f.plural` — "saved N of M documents" — uses a hand-written
  two-way branch in all three languages rather than `f.plural`'s CLDR categories, because English
  "of"/German "von"/Ukrainian "з" each want the *second* number's noun in a fixed case-form (German
  dative, Ukrainian genitive) that does not track the number's own CLDR plural category. Documented
  inline in each catalogue.
- No English literal in a template; no `??` fallback — self-reviewed by reading every new string in
  `bundle.ts`, `panels.ts` and `share.ts`.

**Persistence and the privacy promise**

- The secret is gone from `location` and from `history.state` before the import view renders (#14) —
  the same `navigate(VIEW_PATH, { replace: true })` call the existing single-document share path
  already made, now run before branching on the payload kind rather than after.
- Storage blocked: import reports nothing could be saved rather than claiming success (#21); the
  library's `Share` button simply does not appear when there is nothing to select, which is already
  true whenever storage is blocked (`listLibrary()` resolves to `[]`).
- No new network request. `mintShareEnvelope`/`resolveSelection`/`alreadySavedFlags`/
  `importDocuments` never call `fetch` — enforced by a throwing spy in `test/bundle.test.ts`, the same
  technique `test/crypto.test.ts` uses for `crypto.ts`. The one upload this task can trigger
  (`/api/shares`, for a bundle) goes through `share.ts`'s existing `upload()`, unchanged.

## What should NOT have changed

- **A single ticked document still produces exactly what `openShareModal(text, label)` always
  produced.** `mintShareEnvelope` routes a one-document selection through `seal`, the same function,
  with the same payload shape (`{ text, label, savedAt, exchange? }`) — verified directly (case #4)
  and by `openShareModal`'s own doc comment tracing the call.
- **The existing "share the current document" button is unaffected.** `openShareModal`'s signature
  gained one optional trailing parameter (`exchange`); every existing call site (`main.ts`'s
  `shareDocument()`) compiles and behaves identically unchanged.
- **`main.ts`'s diff is confined to routing.** No change to `load()`, to the document-rendering
  functions, to scroll/history restoration for the document view, or to anything `test/browser/
  nav-scenarios.js`'s existing 24+ scenarios exercise — confirmed by running that suite (see
  `docs/evidence/T6.md`) and by `git diff` against this branch's own base showing the touched
  functions are exactly `showView`, `loadSharedDocument`, and the `view` branch of `applyRoute`.
- **`store.ts` and `crypto.ts` are untouched.** Confirmed by `git diff` against `feat/T5-share-envelope`
  touching neither file.
- **The library's list-mode rows — Open, Rename, Delete — are pixel-for-pixel and behaviourally
  unchanged.** Only their construction was factored into a shared `rowMeta()` helper; the markup it
  produces is identical to before.
