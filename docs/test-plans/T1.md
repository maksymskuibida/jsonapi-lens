# Test plan — T1 Plain JSON

**What this task changes.** `assertJsonApi`'s hard refusal becomes a branch: `detectShape` names what
a pasted document actually is (`jsonapi · hal · odata · jsonrpc · envelope · collection · ndjson ·
plain`) and never throws. A document that is genuinely JSON:API reads exactly as before, with no
extra click. Everything else gets a `JsonIndex` instead of a `DocumentIndex`: inferred collections
drive the same rail the JSON:API path already has, and a repeated identifier — a bare `id`-like key
defining it, a `user_id`-shaped key or a UUID/ULID/ObjectId referencing it — renders as a real link,
the way a `{type, id}` pointer already does.

## Scope

- **In scope:** `detectShape`; `buildJsonIndex` (collections, the identity graph, dangling,
  ambiguous, the node budget); the `AnchorScope` table in `ident.ts` (D1); the plain-JSON render path
  (`render-json.ts`, the `TreeAnnotations` hook in `render-value.ts`, the generalised rail); the
  paste-view shape offer and every other load path's silent fallback to `readAny`; i18n for all of
  the above.
- **Out of scope, and where it is covered instead:** request/response handling (T2); editing,
  filtering or querying JSON (not planned); cross-document identity — matching an id between two
  separately pasted documents, or between a request and its response (T2 at the earliest, and only
  as its own decision — see D2's "What this means for later tasks"); a second value-render path
  (deliberately not built — plain JSON reuses `render-value.ts`); scroll-position restoration for
  plain JSON to the same fidelity as the JSON:API `.res`-section model (see "Known limitations" in
  the QA notes — native fragment scrolling only, by design for this task).

## Edge cases enumerated

**Payload shape**

- Empty input, whitespace only, `{}`, a bare array, a bare string (doubly-encoded), a Python `dict`
  repr, a log line with JSON in the middle, a truncated document — all pre-existing `parseJson`
  behaviour, unmodified, still covered by `test/parse.test.ts`'s original suite.
- `data` absent · `data: null` · `data` as one object · `data` as an array · `data` as something not
  resource-shaped at all (`{"data": 1}`) — the last is the new case (row 6 above).
- `errors` present · `errors` and `data` together (row 7) · `meta` only — all still valid `jsonapi`.
- A duplicate `type:id` in the JSON:API path — untouched, still first-occurrence-wins (pre-existing
  test, unmodified).
- Two definitions of the *same* bare id-like key on one object (`{"id": 5, "code": 5}`) — one
  definition, not two; tested in `test/json-index.test.ts` "does not treat a duplicate id/code pair
  on the same object as two definitions".
- A numeric `42` and a string `"42"` at the same scope — kept distinct, never conflated; tested.

**Identity and anchors**

- A `type`/pointer containing `_`, `__`, `#`, `/`, `.`, `:`, a space, a quote, a newline, or emoji —
  covered by the existing `ident.ts` corpus (unmodified) plus the D1-specific additions in
  `test/ident.test.ts` for the new scope table, and `test/render-json.test.ts`'s hostile-key corpus
  for the plain-JSON render path specifically.
- A `type` deliberately shaped to look like another scope's encoded body — `test/ident.test.ts`
  "cross-scope collision freedom" includes literal lookalikes (`"r_articles__1"`, `"g_articles"`,
  etc.) as segment values in every scope.
- Round-tripping: `parseAnchorId(scope, mintAnchorId(scope, segments))` returns exactly `segments`,
  in every scope, over the hostile corpus — tested.
- All seven scope prefixes are exactly two characters, an ASCII letter and `_`, with distinct first
  characters — tested (`test/ident.test.ts`).
- No static id in `index.html` begins with a scope letter and `_` — tested by parsing the shipped
  markup and checking every `[id]`.

**Injection — on every task that renders anything**

- A hostile value painted through the plain-JSON render path: `<img src=x onerror=alert(1)>`,
  `"><script>alert(1)</script>`, placed in an attribute value and in an identity-linked value —
  tested, appears as text in both places (`test/render-json.test.ts`).
- A URL whose scheme is `javascript:` where `_links.*.href` would otherwise link — tested, never
  becomes an `href`, through the same unmodified `classify()` gate the JSON:API path already relies
  on. `data:` and `vbscript:` are not separately tested here because the gate they would need to pass
  (`classify()`'s `^https?:\/\/` regex, in `format.ts`, untouched by this task) is exactly the same
  one `javascript:` already fails — this task added no new URL-from-payload code path to test
  differently.

**Scale and layout**

- A 200-level-deep document — tested, no stack overflow (the walk is iterative).
- A document past `IDENTITY_NODE_LIMIT` (200,000 nodes) — tested, identity inference is skipped and
  the overview note is shown; **not** benchmarked for actual wall-clock time on a 50 MB paste through
  the real browser — see "Known limitations".
- A collection past `EAGER_BODY_LIMIT` (2,000 members) — capped with a "N more not shown" note rather
  than building every member eagerly. Unlike the JSON:API path, there is no lazy-body toggle to defer
  full detail to on expand (no second render path was built for that); QA by hand to confirm the note
  appears and the page does not hang, not benchmarked precisely.
- Back and Forward on the **JSON:API** path: unaffected by this task, and re-verified by running the
  existing `test/browser/nav-scenarios.js` suite unmodified (see evidence). Back and Forward on the
  **plain-JSON** path: deliberately simpler for this task — native fragment scrolling only, no
  `.res`-section position-restoration model — see "Known limitations".

**Localisation**

- Every new string in `en`, `de`, `uk`; no `??` fallback; no English literal in a template — checked
  by hand across all three catalogues plus `scripts/review-preflight.sh`'s mechanical check.
- German and Ukrainian plurals for every new count-bearing message use the language's own plural
  categories (`{one, other}` for German; `{one, few, many, other}` for Ukrainian), matching the
  existing catalogue's conventions.
- The two static shape-offer button labels are `static-dom.ts` bindings, so `test/i18n.test.ts`'s
  existing "matches the English catalogue exactly" assertion — unmodified — now also covers them.

**Persistence and the privacy promise**

- Reload with a plain-JSON document open: comes back from IndexedDB, read via `readAny` — QA by
  hand (row 25).
- Save to the library and reopen: same document, sensible summary row — automated for the
  determinism property, QA by hand for the actual IndexedDB path (row 24).
- No network request carries payload content — unaffected by this task; nothing in `shape.ts`,
  `json-index.ts`, `render-json.ts` or the `main.ts` changes opens a network connection
  (`scripts/review-preflight.sh`'s network-call check confirms no `fetch`/`XMLHttpRequest`/
  `sendBeacon`/`WebSocket` was added outside `store.ts`/`share.ts`/`crypto.ts`/`worker.ts`).

## Regression fixed in passing — not part of T1's own scope

| # | Scenario | Expected | How verified |
|---|---|---|---|
| 27 | A document is stored from an earlier session; the page is loaded fresh, landing on `/` (the resume banner shows "Still open: …"); click **Back to the document** | The full document view renders — rail, overview, content — not a blank page | QA by hand, and by me directly: reproduced the blank view on the unmodified base commit (`boot()` set `current` via `readAny`/`readDocument` without ever calling `renderLoadedView`, so `showView("doc")` revealed an empty `docEl`), fixed by rendering into `docEl` and folding back to the paste view in the same branch, and confirmed fixed for a fresh load on `/`, for a reload while already on `/view`, and after a language switch (which reloads by design — see `src/i18n/index.ts`) |

**Why this has no automated test.** The buggy branch only runs when `store.ts#loadDocument()`
resolves to a real stored document, and this repository's `vitest` environment (`jsdom`) has no
`indexedDB` — `loadDocument()`'s own `catch` resolves to `null` on that, same as any other storage
failure, so the branch this bug lived in is unreachable in a unit test without either a
`fake-indexeddb` test dependency or restructuring how `main.ts` reaches storage for testability.
Both are bigger than "fix in passing"; flagged to the coordinator rather than done unilaterally.
`main.ts` has no existing `vitest` coverage of its own for the same underlying reason — every
`need("...")` call at module scope requires the real `index.html` structure to already be in the
document, and its behaviour is verified today through `test/browser/nav-scenarios.js` and manual
QA, neither of which currently drives a *second, fresh page load* mid-scenario (`nav-scenarios.js`'s
own README names exactly that as one of the two things still done by hand).

## What should NOT have changed

- **The JSON:API path is byte-for-byte identical.** `DocumentIndex`, `buildIndex`, `readDocument`,
  `assertJsonApi`, `renderDocumentView`, `groupsHtml`, `buildResourceBody`, the `.res`-section
  scroll-restoration model in `main.ts` — none of these were touched in a way that changes their
  output. Every pre-existing test in `parse.test.ts`, `render.test.ts`, `ident.test.ts` and
  `reverse.test.ts` passes with zero edits to those tests.
- **`domId`/`parseDomId`/`resourceHref`/`resourceKey`/`identityFromHash`** keep their exact existing
  behaviour — the D1 scope table is additive, not a rewrite of the `r_` scope.
- **The rail's visual output for a JSON:API document is unchanged** — `renderRail` now takes
  `RailEntry[]` instead of a `DocumentIndex`, but `railEntriesForGroups` reproduces the exact same
  entries `renderRail` used to derive internally, so the rendered markup does not change.
- Back and Forward on a JSON:API document still return the content to the same place on screen — a
  regression here would be the least visible and most damaging failure mode this task could cause,
  since nothing about T1 should touch that model at all.

## Known limitations (see `docs/qa-notes/T1.md` and `docs/evidence/T1.md` for the fuller versions)

- No lazy-body deferral for plain-JSON collection members (capped at `EAGER_BODY_LIMIT`, not deferred
  to on-expand).
- No `.res`-style scroll-position restoration for the plain-JSON view — native fragment scrolling
  only.
- HAL/OData/JSON-RPC get correct shape *detection* and generically-correct rendering (collections
  found automatically, URLs safe automatically) but no bespoke chrome (no dedicated "primary
  collection" styling for OData's `value`, no dedicated errors panel for JSON-RPC's `error`).
- `canonicalScope`'s pluralisation does not know irregular plurals (`person`/`people`) or singulars
  ending in `-se` (`house`, `response`) — documented in `json-index.ts` and D2. The failure mode is
  always "renders dangling instead of linking", never a wrong link.
- The 200,000-node and 2,000-member ceilings are exercised by construction in vitest, not benchmarked
  for wall-clock time against a real multi-megabyte paste in a real browser.
