# Task specification — F3: The share key travels in the fragment, not the path

> Contract level, not line level. From the production QA pass of 2026-09-20 (finding F3, severity
> medium-high, confirmed twice against `https://jsonapi.mstool.dev`). This spec documents `a31d58e`,
> written after the code — see the PR body for how this task came to be implemented before its spec.

## Outcome

A share link's key is never sent to the server, to a proxy, or to anything either of them logs. A
link is `<origin>/d/<id>#<secret>` — the key after a `#`, which a browser strips before it builds
the request and never places in `Referer`. Opening a link, creating one from the share dialog, and
minting one from the MCP `share` tool all produce and consume this form. Links already sent in the
older `/d/<id>:<secret>` (or `.`) shape keep opening, forever — they are still parsed, just never
minted. A URL shaped like a share link but missing a usable key shows a "damaged share link" error
instead of the generic "no page here" toast, because the most likely cause is something along the
way (a chat client, a link shortener, a mail scanner) eating the fragment.

## Interface

`src/router.ts`:

- `shareUrl(id: number, secret: string): string` — now returns `` `${origin}/d/${id}#${secret}` ``.
  Unchanged signature.
- `parseRoute(pathname: string, hash?: string): Route` — the `Route` union gains one member:
  `{ kind: "share-damaged" }`. Existing members (`paste`, `view`, `share`, `legal`, `unknown`) are
  unchanged in shape.
- `SECRET_PATTERN` (new, module-private): `/^[A-Za-z0-9_-]{8,64}$/` — the accepted secret alphabet
  and length, mirrored from `crypto.ts`'s `MIN_SECRET_CHARS`/`MAX_SECRET_CHARS`.

`src/main.ts`: `applyRoute` and `boot` both handle `route.kind === "share-damaged"` by navigating to
`PASTE_PATH`, replacing history, and showing the paste view's error card with
`t().shareErrors.damaged`.

`src/i18n/{en,de,uk}.ts`: `shareErrors.damaged: { headline: string; hint: string }` (new catalogue
entry, all three languages). `share.note` (existing key) is reworded in all three to describe the
fragment.

`src/legal/{en,de,uk}.ts`: `/privacy`'s server-log section gains one paragraph; its share-encryption
section's existing paragraph is reworded. No new keys — same `LegalPages` shape.

`mcp/build-server.ts`, `mcp/descriptions.ts`, `mcp/README.md`: every `<origin>/d/<id>:<secret>`
string becomes `<origin>/d/<id>#<secret>`. No signature or schema change — `shareOutputShape.url` is
still `z.string()`.

## Behaviour

- **Minting.** `shareUrl` and the MCP server's `share` tool are the only two places in the repository
  that build a share link, and both put the secret after `#`. Nothing produces the `:`/`.` form any
  more.
- **Parsing, in order of precedence:**
  1. `/d/<digits>[:.]<secret>` (8–64 chars of `[A-Za-z0-9_-]`), optional trailing slash — the legacy
     in-path form. Matches → `{ kind: "share", id, secret }`.
  2. `/d/<digits>`, optional trailing slash, **with** `hash` (stripped of a leading `#`) matching the
     same secret alphabet/length — the current fragment form. Matches → `{ kind: "share", id,
     secret }`.
  3. Anything else starting `/d/<digit>` — a path that was a share link once but has no usable key
     attached, by either rule above. → `{ kind: "share-damaged" }`.
  4. `/d/<non-digit>...` (e.g. `/d/notanumber:secret`) never reaches rule 3 — it falls through to
     `{ kind: "unknown" }`, unchanged from before this task. It was never a share link, so "no page
     here" remains correct for it.
- **The legacy form is parsed, never minted, forever.** This is permanent, not a deprecation window
  — a link already sent has no way to be un-sent.
- **The damaged-link route is decided from the URL alone.** It never queries the server to
  distinguish "this id exists but the secret is wrong or missing" from "this id never existed" — see
  [DECISIONS.md D7](../DECISIONS.md) and the no-oracle constraint below.
- **`/privacy` says what is true and no more.** The access-log section states the path is what is
  logged, that a fragment cannot appear in a path, and that a link in the legacy format still carries
  its key into that log for as long as anyone uses one. The share-encryption section states the key
  is placed after `#` and is the one part of the address a browser does not transmit. Neither section
  claims the origin cannot obtain the key some other way (it serves the JavaScript that holds it) —
  see D7's "What this does not buy" section.

## Error and edge cases

| Case | Expected |
|---|---|
| `/d/42#AAAAAAAAAAAAAAAAAAAA` (current form, 20-char secret) | `{ kind: "share", id: 42, secret: "AAAAAAAAAAAAAAAAAAAA" }` |
| `/d/42:AAAAAAAAAAAAAAAAAAAA` (legacy `:` form) | Same share route — still parsed, forever |
| `/d/42.AAAAAAAAAAAAAAAAAAAA` (legacy `.` form) | Same share route |
| `/d/42/` (trailing slash) with `#AAAAAAAAAAAAAAAAAAAA` | Same share route — trailing slash tolerated on the id-only path too |
| `/d/42` with no hash at all | `{ kind: "share-damaged" }` — not "no page here" |
| `/d/42` with `#short` (< 8 chars) | `{ kind: "share-damaged" }` |
| `/d/42:short` (legacy form, secret < 8 chars) | `{ kind: "share-damaged" }` |
| A 64-character secret, either form | Still accepted — matches `crypto.ts`'s `MAX_SECRET_CHARS` |
| `/d/notanumber:secret` or `/d/notanumber` | `{ kind: "unknown" }` — never was a share link, unchanged behaviour, "no page here" is still correct |
| `/d/42%3AAAAAAAAAAAAAAAAAAAAA` (percent-encoded colon, from Cloudflare's asset-router redirect on the legacy form) | Decoded before matching, same as `/d/42:AAAAAAAAAAAAAAAAAAAA` |
| `/d/42:AAAAAAAAAAAAAAAAAAAA/extra` (trailing garbage after a legacy-shaped id:secret) | `{ kind: "share-damaged" }` — shaped like a share link, but no rule matches it exactly |
| A 64-character MCP-minted secret round-tripped through `shareUrl`/`parseRoute` | Opens correctly; `mcp/build-server.ts` and the app agree on the same URL shape |
| Opening a link, then Back | The address bar no longer carries the secret in either form once the app has loaded the document (existing behaviour, unchanged by this task) |

## Out of scope

- **Randomising or rotating share ids.** The numeric id is still sequential and still logged in the
  path; only the key moved. Nothing about id predictability changes.
- **Deleting shares whose key was already logged** under the legacy form. The fragment change is
  forward-looking; it cannot retroactively scrub a Cloudflare access log. `/privacy` says this
  plainly rather than implying a cleanup that did not happen.
- **A password or passphrase on the link**, and **deriving the fetch id from the key** — both
  considered and rejected; see D7's "Rejected alternatives".
- **T8's D2** (`docs/task-specs/T8.md`) is fully superseded by the damaged-link route above. T8
  should drop it rather than implement it separately.

## Acceptance criteria

- [x] `shareUrl(id, secret)` returns a URL whose `pathname` is `/d/<id>` and whose `hash` is
      `#<secret>`, and whose `pathname` does not contain the secret.
- [x] `parseRoute` still resolves the legacy `/d/<id>:<secret>` and `/d/<id>.<secret>` forms to
      `{ kind: "share", ... }`, unchanged.
- [x] `parseRoute` resolves `/d/<id>#<secret>` to `{ kind: "share", ... }` for a secret 8–64 chars of
      `[A-Za-z0-9_-]`.
- [x] Every path under `/d/<digits>` that is not covered by the two rules above resolves to
      `{ kind: "share-damaged" }`, not `{ kind: "unknown" }`.
- [x] `/d/<non-digits>...` still resolves to `{ kind: "unknown" }` — the "no page here" path is
      unchanged for a URL that was never a share link.
- [x] Visiting a damaged share link shows the paste view with the `shareErrors.damaged` error card,
      not the `toast.noPage` toast, and the address bar is replaced with `/`.
- [x] The MCP `share` tool's returned `url` field, and every string in `mcp/descriptions.ts` and
      `mcp/README.md` describing the URL shape, use `#`, not `:`.
- [x] `shareErrors.damaged`, and the reworded `share.note`, exist in `en`, `de` and `uk` with no
      fallback and no English literal in a template.
- [x] `/privacy` in all three languages states: the log records the path; the path cannot contain a
      key; a legacy-format link still logs its key while it is used. No sentence claims more than
      that (e.g. no claim that the origin itself cannot see the key, which D7 explicitly disclaims).
      **Fix round 1 (review B2):** the opening sentence originally claimed this unconditionally —
      "the path in that log never contains the key" — before the legacy-format admission three
      sentences later contradicted it. Reworded in all three languages to scope the claim to a link
      *created here* (`src/legal/en.ts`, `de.ts`, `uk.ts`), so the two facts refine each other
      instead of opposing.
- [x] `DECISIONS.md` D7 exists and matches the implementation described above.
