# Task specification — T7: MCP server — share and read

> Contract level, not line level. Depends on **T5** (the versioned envelope and the bundle payload).

## Outcome

An assistant can put a document — or several — behind a jsonapi-lens share link, and read one back,
without a browser. It generates the encryption key itself, so the ciphertext is readable by whoever
it gives the link to and by nobody else, including the server.

## Interface

A stdio MCP server under a new `mcp/` tree. Two tools.

### `share`

```
share({
  documents: [{ label: string, text: string, exchange?: Exchange }],   // 1..n
  secret:    string,        // 64 lowercase hex characters
  lifetime?: "15m" | "6h" | "1d" | "1w" | "1m" | "forever",   // default "1d"
  origin?:   string         // default https://jsonapi.mstool.dev
}) -> { id: number, url: string, expiresAt: number | null, bytes: number, kind: "document" | "bundle" }
```

- **One document seals as a version-2 single share; several seal as a version-3 bundle.** Same rule
  as the UI, and the same bytes — a link minted here must open in the browser and vice versa.
- **The caller supplies the secret; the server never invents one.** The tool's description must say,
  in the words the model will read:

  > Generate the secret yourself before calling this, with `openssl rand -hex 32`. Keep it — it is
  > not recoverable from the id, and the server cannot decrypt without it. The link is
  > `<origin>/d/<id>:<secret>`, for example `https://jsonapi.mstool.dev/d/412:a1b2…`. Anyone with
  > that link can read the document; anyone with only the id cannot.

  Say it in the description rather than only in these docs, because the description is the only part
  the model sees.
- `url` is returned as a convenience and is exactly `<origin>/d/<id>:<secret>`. Returning it does
  not weaken anything — the caller already holds both halves — and it removes a formatting mistake
  from the one step that cannot be retried.

### `read`

```
read({ id: number, secret: string, origin?: string })
  -> { kind: "document", label, savedAt, text, exchange? }
   | { kind: "bundle",   savedAt, documents: [{ label, text, exchange? }] }
```

Fetches, decrypts, and returns the payload as it was sealed. No parsing, no reshaping — a document
comes back as the text that went in.

## Behaviour

**One crypto implementation, not two.** The server imports the project's own `src/crypto.ts`. A
second implementation would drift, and the drift would show up as links that mint here and refuse to
open in a browser. Two consequences to handle rather than avoid:

- `crypto.ts` reads its error strings through `t()`. The server sets the locale to `en` once at
  startup. Do not refactor `crypto.ts` to remove the dependency — that is a bigger change than this
  task, and the coupling costs nothing here.
- `seal`/`open` use WebCrypto and `CompressionStream`, both present in Node 22, which is what CI
  uses. State the minimum Node version in `mcp/README.md` and fail with a readable message on an
  older one rather than a `TypeError` about `undefined`.

**The transport is the existing public API.** `POST /api/shares?lifetime=…` with the ciphertext, and
`GET /api/shares/<id>`. No new endpoint, no credential, no privileged path — this server is just
another client, and the 12 MB ciphertext cap applies to it exactly as it does to the browser.

**The network rule in `docs/PROCESS.md` §5 is about `src/`.** It says no module outside
`store.ts`/`share.ts`/`crypto.ts` opens a client connection, and it exists to keep *reading a
document in the browser* local. `mcp/` is a separate program the user runs deliberately; it may
fetch. Add a sentence to §5 saying so, so the next reader does not have to work out whether the rule
was broken.

**Secrets are never persisted or logged.** Not to stdout, not to stderr, not to a debug line, not
into an error message. The `url` in a result carries the secret by construction and that is the
point; nothing else may. A test asserts no log line contains the secret.

## Error and edge cases

| Case | Expected |
|---|---|
| `documents` empty | Refused, naming the requirement. Not an empty bundle |
| `documents` with one entry | Version-2 single share, `kind: "document"` |
| A document with empty `text` | Refused — an empty document is not shareable |
| `secret` not 64 hex characters | Refused, with the exact expectation and the `openssl rand -hex 32` command. **Never fall back to generating one** — a caller that thinks it knows the secret and does not has minted an unreadable link |
| `secret` uppercase hex | Refused, or normalised — pick one, say which, and be consistent between `share` and `read`, because a mismatch is an unopenable link |
| `lifetime` not in the table | Refused, listing the accepted values. The Worker's table is the authority |
| Ciphertext over 12 MB | Refused before upload, naming which documents are largest and the overage |
| The upload fails, or returns non-2xx | The server's own error text surfaced verbatim, with the status. No retry on a 4xx |
| `read` with an unknown id | The 404 reported as "gone or never existed" — the same message for both, since the Worker cannot distinguish them and guessing would be an oracle |
| `read` with an expired id | The 410 reported as expired |
| `read` with the wrong secret | Decryption failure, **indistinguishable from a corrupt blob**. Do not report which |
| `read` of a version the build does not know | The existing wrong-version error, naming both numbers |
| `read` of a bundle | `kind: "bundle"` with every entry; never silently the first one |
| `origin` pointing somewhere that is not jsonapi-lens | Whatever the fetch returns, reported plainly. Do not follow redirects to a different host |
| `origin` with a path or a query | Refused — it is an origin, and accepting a path invites a mistake that uploads somewhere unintended |
| A document text of 5 MB | Works; the gzip in `seal` is what makes it fit |
| Node older than the minimum | A readable message naming the version needed, at startup |

## Out of scope

- Reading a document from disk, a URL, or the user's browser storage. Text comes in through the tool
  call.
- Parsing, indexing, validating or summarising a document. That is what the browser is for. `read`
  returns text.
- Deleting or revoking a share. The Worker has no such endpoint and this task does not add one.
- Listing shares. There is deliberately nothing to list — the D1 table holds no descriptive data.
- Generating secrets. The caller does that, and the tool descriptions say how.
- Any change to the Worker, D1, or the envelope. **T5** owns the envelope.

## Acceptance criteria

- [ ] `share` with one document returns an id and a URL that **opens in a browser** and renders the document.
- [ ] `share` with three documents returns a URL that opens the bundle import view with all three.
- [ ] A link minted in the **browser** is readable by `read`, and a link minted by `share` is readable by the browser. Both directions, asserted end to end.
- [ ] `read` returns the text byte-for-byte as it was passed to `share`.
- [ ] A 63-, 65-character or non-hex secret is refused, and the message contains `openssl rand -hex 32`.
- [ ] A wrong secret and a corrupt blob produce the same failure.
- [ ] No log line, error message or result field other than `url` contains the secret.
- [ ] The tool descriptions state how to build the URL and that the secret is unrecoverable — checked by reading the registered schema, not the source comments.
- [ ] `mcp/README.md` says how to register the server, the minimum Node version, and what the server can and cannot see.
- [ ] `docs/PROCESS.md` §5 says that `mcp/` may open a network connection and why that does not weaken the promise about `src/`.

## Tests that must exist

- [ ] Round trip against a **stub** of `/api/shares` that records the bytes: `share` then `open` with the same secret yields the original documents.
- [ ] Cross-compatibility, both directions, against the browser's own `seal`/`open` — the same fixture, the same secret, and each side reading the other's bytes. This is the test that stops the two implementations drifting.
- [ ] One document seals with version byte 2; several with version byte 3. Asserted on the bytes.
- [ ] Secret validation: 64 hex accepted; 63, 65, non-hex, empty and uppercase each handled exactly as the table says.
- [ ] Every error row in the table above, including that 404 and a wrong secret do not reveal which happened.
- [ ] A test that greps everything written to stdout and stderr during a full `share` + `read` run and asserts the secret does not appear.
- [ ] `lifetime` outside the Worker's table is refused before any network call is attempted.
- [ ] An `origin` carrying a path is refused.
- [ ] No test touches the real deployment: every network call goes through the stub, asserted by failing if a real fetch is attempted.
