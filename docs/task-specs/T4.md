# Task specification — T4: Diagnostics

> Contract level, not line level. Depends on **T2** (the model and the review) and reads better with
> **T3** (importers), but does not require it.

## Outcome

The request explains the response. This tool's most useful signal is *a pointer that resolves to
nothing*, and the commonest cause is an `include` that never asked for it — today that is a guess
you go and check. With both halves indexed it becomes an answer, linked at both ends.

## Interface

```
Finding {
  check:    CheckId
  verdict:  "consistent" | "unrequested" | "missing" | "contradicted" | "unknown"
  subject:  string                  // what it is about, for the f_ anchor
  requestAnchor?:  string           // e.g. the include parameter's q_ id
  responseAnchors: string[]         // resources or rows the finding is about
}

runChecks(exchange: Exchange): Finding[]
```

Findings are **data, not prose** — the sentence is a catalogue entry keyed by `check` and `verdict`,
so all three languages get it and no English lands in the code. Anchored under the `f_` scope per
[D1](../DECISIONS.md).

## Behaviour

Checks run only when both sides carry what they need; a check that cannot run is **absent**, not
`unknown` — a page of "could not determine" teaches people to stop reading. `unknown` is reserved
for a check that *can* run but cannot decide, and it says why.

| Check | Compares | Verdicts |
|---|---|---|
| `include-vs-included` | each `include` path against `included` | `missing` (asked, absent) · `unrequested` (a dangling pointer whose type no `include` path names) · `consistent` |
| `fields-vs-attributes` | `fields[type]` against attributes actually returned | `missing` (asked, absent) · `unrequested` (returned outside the fieldset) |
| `sort-vs-order` | `sort` against the order of `data` | `contradicted` naming the first inverted pair · `consistent` · `unknown` when the sort key is not an attribute of every member |
| `page-vs-count` | `page[size]`/`limit` against resources returned, `meta.total`, `links.next`/`prev` | `consistent` · `contradicted` |
| `filter-vs-data` | plain-equality filters against returned resources | `contradicted` · `unknown` for an operator it cannot evaluate |
| `status-vs-body` | status against document shape | `contradicted` for a 2xx carrying `errors`, a 4xx/5xx with no `errors` member, a 404 with `data: null` |
| `content-type` | response `Content-Type` against the document, and request `Accept` against both | `contradicted` for `application/json` on a JSON:API document, or an `Accept` that never asked for `vnd.api+json` |
| `content-length` | declared `Content-Length` against the body's byte length | `contradicted` with both numbers |
| `sent-vs-returned` | a `POST`/`PATCH` request body's resource against the response's, attribute by attribute | per-attribute `consistent`/`contradicted`/`missing` — the check that answers "did it save what I sent?" |
| `token-vs-status` | a decoded `exp` against the response timestamp, on a 401/403 | `contradicted` when the token had already expired |

**`unrequested` is the headline check**, because it converts the tool's existing amber signal into an
explanation: *12 pointers to `operators` resolve to nothing — `include=legs.station` never asks for
them. Add `legs.operator`.* And it must be able to say the opposite just as clearly: the pointer is
dangling and the `include` **did** ask, so the server dropped it and this one is not you.

**Findings appear where they matter, not only in a list.** The band's closed line carries a count.
The existing unresolved-pointers panel gains a cause column. A resource whose attributes fall
outside `fields[type]` says so on its own row. The list is the index; the inline sentence is what
gets read.

## Error and edge cases

| Case | Expected |
|---|---|
| No request | No checks, no count, no empty panel |
| Request with no query and no headers | No checks, and no "0 findings" chrome |
| `include` present, `included` absent entirely | `missing` for every path |
| `included` present, no `include` parameter | Not a finding — a server may include by default |
| A dangling pointer whose type **is** named by `include` | `contradicted` against the server, and said so plainly |
| `include=a.b.c` with `a` present and `b` absent | `missing` at `a.b`, and the deeper path not reported twice |
| `fields[type]` for a type not in the response | `unknown`, naming it |
| `sort` on an attribute some members lack | `unknown` with the count that lack it |
| `sort` with a locale-sensitive string key | Compared with `localeCompare`, and the fact stated |
| `page[size]` larger than the count, with no `links.next` | `consistent` — a short last page is correct |
| `page[size]` equal to the count, with no `links.next` | `unknown`, not a defect: it may be an exact last page |
| A 200 with `errors` | `contradicted`, critical enough to lead the list |
| A 204 with any body | `contradicted` |
| `Content-Length` absent | Check absent |
| A `sent-vs-returned` server-generated attribute (`createdAt`, `id`) | Not a contradiction — server-assigned fields are excluded and the exclusion is named |
| 50k resources | Checks respect a budget; over it they are skipped with a note, never stall |
| A finding whose subject contains hostile text | Rendered as text; the `f_` anchor encodes through `ident.ts` |
| Two findings with the same `check` and `subject` | One anchor, deduplicated |

## Out of scope

- Fixing anything. A finding is a navigation aid, never an edit.
- Validating the document against the JSON:API spec generally — that is a different tool.
- OpenAPI or schema-based validation.
- Any network call. Checks are pure functions over an `Exchange`.

## Acceptance criteria

- [ ] With `include=legs.station` and dangling `operators` pointers, the finding names the missing `include` path and links to both the parameter row and the dangling panel.
- [ ] With `include=legs.operator` and dangling `operators` pointers, the finding says the server dropped them.
- [ ] A 200 carrying `errors` leads the list.
- [ ] `sort` contradicted names the first inverted pair by position.
- [ ] A `POST` body's resource is compared attribute-by-attribute with the response's, with server-assigned fields excluded and named.
- [ ] Every finding sentence exists in `en`, `de` and `uk`; no English in `src/` outside the catalogues.
- [ ] A check that cannot run produces nothing at all, not an `unknown` row.
- [ ] `docs/evidence/T4.md` records a browser run at the branch-head SHA it was performed at.

## Tests that must exist

- [ ] `runChecks` is a pure function: called twice on one exchange it returns deeply equal findings, and it opens no network connection.
- [ ] One test per row of the check table, asserting the `verdict` and the anchors — not merely that a finding appeared.
- [ ] Every row of the edge-case table above.
- [ ] `include=a.b.c` with `b` absent reports exactly one finding, at `a.b`.
- [ ] `page[size]` equal to the returned count with no `links.next` is `unknown`, not `contradicted` — the case where an over-eager check would cry wolf on a correct exact-page response.
- [ ] A 50k-resource exchange skips the checks within the budget and says so.
- [ ] Findings with the same check and subject deduplicate to one anchor.
- [ ] A hostile finding subject renders as text and produces a valid, unique `f_` id.
