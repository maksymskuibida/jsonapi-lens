# Task specification — T9: The preflight flags its own test fixtures

> Contract level. Started small and self-contained — one file — and grew twice during review, both
> times because the reviewer traced the same root cause one level deeper than this spec originally
> did. See "Scope growth" below. The spec is updated in the same pull request as the code, per
> `.claude/agents/implementer.md`: a spec that no longer matches shipped behaviour is worse than none.

## Outcome

`scripts/review-preflight.sh` stops reporting findings against test data that exists precisely to
contain the patterns it looks for, resolves the base it diffs against instead of assuming it, and no
longer filters `check` on the pull request's base branch — so a pull request whose own merge ref
carries this trigger runs `check` no matter what it targets. That last part is a narrower claim than
it sounds: see "The `pull_request` trigger" below for what it does and does not do for a pull request
that is already open and stacked on a branch that predates this change.

## Scope growth

Two additions landed on top of the original fix, both raised by the coordinator during review of this
same change, both real:

1. **Base-ref resolution** (`scripts/review-preflight.sh`). The original defect (below) was diagnosed
   as symptom of the attack suite planting trigger patterns as fixtures. It is also a symptom of a
   second, deeper cause: `BASE_REF` was the literal constant `origin/main`, but this repository's
   implementer branches fork from a shared integration branch, not from `main` directly — so `main`
   does not yet contain that branch's own commits, and a hardcoded `origin/main` always diffs against
   a stale ancestor. Fixing only *what* each invariant reads (the original fix) does not fix *where*
   the diff starts. Both are needed.
2. **The `pull_request` trigger filtered on the wrong branch** (`.github/workflows/deploy.yml`). Not a
   defect in the preflight script at all, but the same class of bug — a gate that does not run is
   indistinguishable from a gate that passes — found while investigating why every branch's diff
   carries commits `main` does not have: `pull_request: branches: [main]` filters on the PR's *base*
   branch, so a pull request stacked on another feature branch (rather than opened directly against
   `main`) triggered **no workflow at all**, silently. `docs/PROCESS.md` §8 claimed CI runs on a pull
   request; that was false for exactly the PRs this repository actually opens during a wave, since
   several implementer branches stack on top of each other by design. `.github/` is out of the
   implementer brief's normal bounds; the coordinator authorised this one change explicitly, for this
   reason, and it is called out prominently in the pull request body.

Both are described in their own subsections below rather than folded silently into the original
prose, so the acceptance criteria stay traceable to why each one exists.

## Corrections from review

Three blockers and two of the reviewer's own suggestions, all fixed in the same pull request rather
than a follow-up, because two of the three blockers were the exact hazard scoping-by-file-location
was supposed to guard against and not introduce:

1. **B1 — `index.html` dropped out of the innerHTML and href invariants.** `DIFF_SRC` (the pathspec
   backing the innerHTML/insertAdjacentHTML scan and the href note) read `-- src`, not `-- src
   index.html` — inconsistent with `src_touched` and the evidence-staleness diff two sections of the
   same script over, both of which already treat `src/` and `index.html` as one thing: shipped
   application code. Verified in review: an `innerHTML` assignment inside an inline `<script>` in
   `index.html`, and an `href="${…}"` added there, were caught by the pre-T9 gate and missed by this
   one — a regression on the check `docs/PROCESS.md` §4 names as highest-severity. Fixed by adding
   `index.html` to the pathspec; a new case (index.html innerHTML beside the attack suite) covers it.
2. **B2 — the jsdom-altitude gate condition, `^test/[^b]`, excludes every test file whose name begins
   with "b", not `test/browser/`.** Pre-existing (not introduced by this task), but this task rewrote
   the block immediately below it and added a comment asserting the correct semantics the code did
   not have — worse than an unexplained bug, because it actively misleads the next reader. T6 is
   "share bundle", so a layout assertion in `test/bundle.test.ts` was silently never scanned. Fixed by
   deriving the gate from the identical pathspec that already builds `ADDED_TEST_UNIT`, so the two
   cannot drift apart again; a new case (`test/bundle.test.ts`) covers it.
3. **B3 — the corrected `PROCESS.md` §8 row, and this spec's own "Behaviour" section, overclaimed in
   the same direction the row was corrected on behalf of.** A `pull_request` event is evaluated from
   the PR's **merge ref** (head merged into base), never from the base branch — proved from this
   repository's own data (`origin/main`'s workflow has no `pull_request:` trigger at all, yet a PR
   based on `main` produced a real `pull_request`-event run) rather than from documentation. This
   means merging this PR gives **zero** checks to a pull request that is already open and stacked on
   a branch predating this fix — its merge ref does not contain `main`, so nothing about the fix
   reaches it. See "Behaviour — the `pull_request` trigger" below for the corrected explanation, and
   `docs/DELIVERY.md`'s release sequence for the operational consequence (an earlier commit on the
   integration branch, `e5f11b3`, drew the right conclusion — un-stack before merging — from the wrong
   mechanism; this task corrects the mechanism and keeps the conclusion, adding the `pull_request:
   edited` event-type caveat that the wrong mechanism would otherwise have missed).
4. **S1 — the same-named-upstream fix (§1 above) compares branch names, so the identical bug survives
   under a different local name.** Checking this exact branch out under a new name
   (`git checkout -b review-4 origin/<branch>`) keeps `@{u}` pointing at the original upstream under
   its original name; reproduced live, on this actual pull request's branch, during review. The
   condition that matters is identity, not naming — does the candidate already contain `HEAD` — so an
   ancestry check (`git merge-base --is-ancestor HEAD "$upstream"`) is added alongside the name check,
   which still covers the "same branch, remote behind" shape the ancestry check alone would not. A new
   case (a differently-named ref pointing at `HEAD`'s own commit) covers it.
5. **S3 — `docs/PROCESS.md` §3 says all nine deliverables are required unconditionally, which is now
   knowably false about the gate shipped beside it.** `scripts/review-preflight.sh` already treats the
   test plan, QA notes and evidence file as required only when `src/` or `index.html` changed — this
   task's own PR is the proof, since it has none of the latter two by design (see "Out of scope" and
   the pull request body) and the gate does not block on their absence. §3 is corrected to state the
   exception the gate already enforces, rather than leaving the next reviewer to rediscover it.

## The defect (original scope)

T1's implementer traced all four of its preflight findings to `scripts/attack-preflight.sh`, which
literally contains `<<<<<<<`, `.only(`, `innerHTML` and `scrollY` — because those are the defects it
plants to prove the gate catches them. So any diff that touches the attack suite reports conflict
markers, a focused test, an `innerHTML` path and a jsdom layout assertion, none of which are real.

**Why this matters more than the noise.** Four false findings on a clean diff is how a reviewer
learns that this gate's output is decoration, and that lesson transfers to the findings that are
real. It is the same failure as an over-eager check crying wolf, and this project has already spent
a review round on a gate that *silently passed* — the opposite error, from the same root: nobody
had checked what the check actually reads.

**This is not actually self-limiting, which the original draft of this spec got wrong.** It said the
false findings would stop once T0 merges, because `origin/main` would then contain the attack suite
and it would no longer be new content in every diff. That is true only for the fixture data itself.
It does not hold for prose that legitimately discusses these patterns as examples — `PROCESS.md` and
the agent briefs describe the innerHTML rule, the conflict-marker check and the focused-test check in
exactly the words that trip them — so scoping by *file location* (below) rather than waiting for a
merge is the only fix that does not recur on the next edit to that paragraph. It also does not hold
for `review-preflight.sh`'s own pattern-definition lines, which necessarily contain the literal
strings they search for; those settle the same way the fixture data does — once merged, an unchanged
line is no longer "added" — but a future edit to those exact lines (as this change makes) will
self-match again. That residual is accepted, not fixed, because avoiding it would mean rewording the
gate's own regex definitions, which is changing what a check looks for — explicitly out of scope.

## Behaviour — file-scoped invariants (original scope)

The **code invariants** — the `innerHTML`/`insertAdjacentHTML` scan, the `href` note, the network-call
scan, the DOM-id scan, the hardcoded-copy scan, and the jsdom-altitude scan — are assertions about
**application code**. They must read only the files those invariants govern, and must not read the
gate's own test data. In practice this means an inclusion pathspec (`git diff ... -- src index.html`,
`git diff ... -- test ':!test/browser'`), not an exclusion of the attack suite specifically — an
inclusion cannot be widened by accident to cover a file it shouldn't, and it is what also keeps these
checks quiet on documentation prose that discusses the same patterns (see above). "Application code"
means `index.html` as much as `src/` — it is the 500+ lines of shipped markup `vite build` ships as
the document, with real `href`s, real DOM ids and an inline `<script>` — and writing the pathspec as
`-- src` alone, without `index.html`, was a real regression caught in review (see "Corrections from
review" B1); every other place in this same script that means "shipped application code" already
said both.

The **hygiene checks** that are genuinely about any file — conflict markers, and focused or skipped
tests — need a different treatment, because a real conflict marker in a script is a real problem. For
those, exclude the attack suite specifically, and say in a comment why that one file is exempt. These
two stay asymmetric with the code invariants on purpose: they are supposed to fire on any file, so an
inclusion pathspec would be the wrong shape for them.

Nothing about which patterns are searched changes. Only where they are searched.

## Behaviour — base-ref resolution (scope addition 1)

`BASE_REF` is resolved in order of trust, each candidate verified before use, instead of assumed:

1. The pull request's own base branch, when a PR number is given (`gh pr view <n> --json
   baseRefName`) — ground truth for what the diff will actually be evaluated against on merge.
2. The branch this one tracks (`@{u}`), when one is configured **and it is not simply this same
   branch's own copy of itself on the remote.** `git push -u origin <branch>` — how a branch actually
   reaches the remote in this repository, including this one — sets `@{u}` to exactly that: a
   same-named mirror, not whatever the branch was forked from. Trusting it unconditionally was tried,
   shipped in an earlier commit on this same task, and immediately broke self-review on this exact
   branch right after it was pushed: `origin/fix/T9-preflight-self-fixtures` differed from `HEAD` by
   nothing, so the script reported "no changes" instead of the real diff. Fixed by comparing branch
   names and discarding `@{u}` when they match, before it is ever fetched or verified.
3. `origin/main`, the repository's actual default branch.

A candidate that does not resolve (network failure, `gh` unavailable or unauthenticated, no upstream
configured or a same-named one, PR not found) is skipped, not fatal — only exhausting all three is. The script still fails
closed: if no candidate resolves to a real ref, or the resolved ref shares no merge-base with `HEAD`,
it exits 2 with a stated reason. It never falls back to exit 0 "skipping" — that would turn a
resolution failure into a silent pass, which is the one thing this script exists not to do.

## Behaviour — the `pull_request` trigger (scope addition 2)

`.github/workflows/deploy.yml`'s `pull_request` trigger drops its `branches: [main]` filter. The
`deploy` job's guard (`if: github.event_name != 'pull_request'`) is unaffected — it keys on the event
type, not the base branch, so it stays unreachable from any pull-request-triggered run. The
`concurrency.group` expression (`format('pr-{0}', github.ref)` for pull-request events) is also
unaffected: `github.ref` for a `pull_request` event is always the PR's merge ref, set by the platform
regardless of base branch, so the group name is never empty.

**What this does and does not do for an already-open pull request — corrected during review, because
the first draft of this section got the mechanism backwards.** GitHub evaluates the workflow for a
`pull_request` event from the PR's **merge ref** — head merged into base — never from the base branch
alone. (This is also why `pull_request_target` exists: it is the variant that reads from the base,
specifically so a workflow can run trusted logic against an untrusted fork without executing that
fork's own workflow changes.) One consequence is favourable and was the original, correct point:
`check` now runs for a pull request regardless of what its base branch is, **once the trigger removal
is present in that PR's own merge ref** — which happens automatically for any *new* pull request
opened after this merges to `main`, because its merge ref then contains the fix through its base.

The consequence that was originally missed: **merging this PR does nothing for a pull request that is
already open and stacked on a branch that predates this change.** Its merge ref is that branch's head
merged into that branch's own base — not `main` — so nothing about this fix enters it. Such a PR has
zero checks before this merges and zero checks after, until the fix reaches **its own** head or base:
by merging or rebasing updated `main` into it, or by re-targeting it at `main` (`docs/DELIVERY.md`
§"Release sequence" step 3a). And re-targeting alone may not be enough to make a run appear: the
default `pull_request` activity types are `opened, synchronize, reopened`; changing a PR's base is
`edited`, which is not among them — a push (which a rebase provides) or a close/reopen may be needed
to actually fire a run.

`docs/PROCESS.md` §8's "CI runs on a pull request" row, and `docs/DELIVERY.md`'s release sequence,
are corrected to state this precisely.

## Error and edge cases

| Case | Expected |
|---|---|
| A diff touching only `scripts/attack-preflight.sh` | No code-invariant findings |
| A real `innerHTML` in `src/` **and** the attack suite in the same diff | The `src/` one is still reported |
| A real conflict marker in `scripts/review-preflight.sh` | Still reported — only the attack suite is exempt from that check |
| A real `it.only` added to `test/` | Still reported |
| A diff touching neither `src/` nor `scripts/` | Unchanged behaviour |
| A diff that is only documentation | Unchanged behaviour |
| The exclusion written as a path prefix | Must not accidentally exempt a future `scripts/attack-*.sh` that is not the suite, or any file under `src/` |
| `innerHTML` mentioned as prose in a Markdown file, no `src/` change | No code-invariant findings — the "self-limiting" case that does not actually resolve on its own (see above) |
| A PR number is given and `gh` can resolve its base branch | The diff is computed against that base, not `origin/main` |
| No PR number, no upstream configured, `origin/main` unresolvable | Exit 2 with a stated reason — never exit 0 |
| A pull request whose own merge ref carries this trigger, targeting a non-`main` base | `check` still runs; `deploy` still does not |
| A pull request opened **before** this merges, stacked on a branch that predates it | No change from merging this PR — its merge ref does not contain the fix. Not a code-invariant scenario; documented in "Behaviour — the `pull_request` trigger", not covered by an attack-suite case |
| The configured upstream (`@{u}`) is this same branch's own copy of itself on the remote — the ordinary result of `git push -u` | Discarded; falls through to `origin/main` rather than reporting "no changes" |
| The configured upstream is a **differently-named** ref that already contains `HEAD` — this branch checked out locally under another name | Discarded by identity (`git merge-base --is-ancestor HEAD "$upstream"`), not by name; falls through to `origin/main` |
| A real `innerHTML` in an inline `<script>` in `index.html` **and** the attack suite in the same diff | Still reported — `index.html` is application code, same as `src/` |
| A layout assertion in a vitest spec whose name begins with "b" (e.g. `test/bundle.test.ts`) | Still reported — the gate condition must not exclude it |

## Out of scope

- Changing which patterns any check looks for, or adding a check. This includes not rewording
  `review-preflight.sh`'s own conflict-marker and focused-test regex literals to dodge their own
  check — the residual self-match those two lines produce until this exact edit merges is accepted,
  per "The defect" above, not patched around.
- The evidence-staleness check, the git-ignored-file check, and the required-artifact checks — none
  of them read added lines, so none are affected.
- `scripts/attack-preflight.sh` itself. Do not edit the suite to hide from the gate; fix the gate.
- `.github/`, `src/`, `test/`, `index.html`, `migrations/` — the implementer's normal bounds — **with
  one explicit, narrow exception**: the `pull_request` trigger fix in `.github/workflows/deploy.yml`
  (scope addition 2), authorised by the coordinator for the specific reason given above, and confined
  to removing one `branches:` filter plus the accompanying comment. No other line in that file
  changes.

## Acceptance criteria

- [ ] A diff whose only change is to `scripts/attack-preflight.sh` produces **zero** code-invariant findings.
- [ ] A diff containing both a real `src/` violation and the attack suite still reports the `src/` one.
- [ ] A diff containing both a real `index.html` violation and the attack suite still reports the `index.html` one — `index.html` is application code, not just `src/` (B1).
- [ ] A layout assertion in a vitest spec whose name begins with "b" is still reported; the gate condition is derived from the same pathspec as the scan it guards, so the two cannot drift apart again (B2).
- [ ] `innerHTML` (or any other code-invariant pattern) mentioned as prose in a Markdown-only diff produces **zero** code-invariant findings.
- [ ] Given a PR number whose base `gh` can resolve, the diff is computed against that base, not against a stale `origin/main`.
- [ ] With no PR number, no upstream, and no resolvable `origin/main`, the script exits 2 with a readable reason — never 0.
- [ ] A same-named upstream is discarded whether reached via `git push -u` or via checking this branch out locally under a **different** name — identity, not naming, is what is checked (S1).
- [ ] `scripts/attack-preflight.sh` reports **44 passed, 0 failed** (26 original + 18 new: 7 attack-suite-only code-invariant/hygiene assertions, 1 attack-suite-only jsdom-altitude, 1 real-src/-violation-beside-the-suite, 1 conflict-marker-elsewhere, 1 similarly-named-script ceiling, 1 doc-prose, 2 base-ref resolution, 1 same-named-upstream ceiling, 1 real-index.html-violation-beside-the-suite, 1 bundle.test.ts layout assertion, 1 differently-named-upstream-by-identity ceiling; see the suite for the exact breakdown).
- [ ] A gate stubbed dead — at `exit 2`, `exit 1` **and** `exit 0` — still takes all 44 cases down — no exclusion or new resolution path has created a case that passes vacuously, and none passes on exit status alone regardless of which exit code the gate returns.
- [ ] The comment in the script says which file is exempt from which check and why, and separately documents the base-ref resolution order and why it fails closed.
- [ ] `.github/workflows/deploy.yml`'s `pull_request` trigger no longer filters on `branches: [main]`, so `check` runs for any pull request whose own merge ref carries this trigger — which means every *new* pull request after this merges, not an already-open one stacked on a branch that predates it (see "Behaviour — the `pull_request` trigger" above). `deploy` remains unreachable from any pull-request-triggered run; `actionlint` reports no findings against the file.
- [ ] `docs/PROCESS.md` §8's "CI runs on a pull request" row states the corrected, precise claim.

## Tests that must exist

Add them to `scripts/attack-preflight.sh`, which is where this gate's tests live.

- [ ] A case whose diff touches only the attack suite, asserting the run is clean of code-invariant findings — and asserting it by the absence of those specific finding messages plus the presence of each check's own `ok` line, never by the exit status alone. A case that only checks the exit code passes against a dead gate, which is a mistake this suite has already made once and fixed.
- [ ] A case with a real `src/` violation **and** the attack suite in one diff, asserting the real one is still found.
- [ ] A case with a genuine conflict marker in a non-exempt script, asserting it is still found.
- [ ] A case with a genuine conflict marker in a script similarly named to, but not, the attack suite (`scripts/attack-other.sh`), asserting it is still found — proves the exemption is one literal path, not a glob.
- [ ] A case whose diff touches only a Markdown file containing `innerHTML` as prose, asserting the innerHTML invariant is clean via its own `ok` line — proves the "self-limiting" framing in the original defect description was incomplete.
- [ ] A case in which a PR's real base (stubbed `gh`) differs from `origin/main` and carries content `origin/main` lacks, asserting the diff is computed against the real base and the stale content is absent.
- [ ] A case in which every base-ref candidate is exhausted (no resolvable PR base, no upstream, no `origin/main`), asserting exit 2 with a readable reason.
- [ ] A case in which the configured upstream is this same branch's own copy of itself on the remote (the shape `git push -u` actually produces), asserting the resolver discards it and falls through to `origin/main` rather than reporting "no changes" — this is not a hypothetical: it broke self-review on this task's own branch during implementation.
- [ ] A case with a real `innerHTML` violation in `index.html` **and** the attack suite in one diff, asserting the real one is still found — proves `index.html` is read as application code, not just `src/` (B1; not a hypothetical, caught in review as a genuine regression).
- [ ] A case with a layout assertion in a vitest spec whose name begins with "b" (`test/bundle.test.ts`), asserting it is still found — proves the gate condition and the scan it guards cannot drift apart again (B2; not a hypothetical, caught in review as a genuine gap that predates this task).
- [ ] A case in which the configured upstream is a **differently-named** ref that already contains `HEAD` — this branch's own content under another name, not reached via `git push -u` — asserting the resolver discards it by identity and falls through to `origin/main` (S1; not a hypothetical, reproduced live against this task's own branch during review by checking it out under a different local name).

There is no automatable test for the `.github/workflows/deploy.yml` trigger fix itself — GitHub only
evaluates `branches:` filters on its own platform, not locally. `actionlint` (run locally; not
previously a dependency of this repository) verifies the YAML and expressions are well-formed and
that `deploy`'s guard and the `concurrency` expression are unaffected.

**What confirms the trigger fix for a pull request stacked on a non-`main` base, and what does
not.** Merging this PR is not that confirmation: a `pull_request` event reads the workflow from that
PR's own merge ref, and no PR open before this merges has this fix in its merge ref — so nothing
observable changes for one of those at the moment of merge (see "Behaviour — the `pull_request`
trigger" above). What would confirm it is a run that actually fires for a pull request whose base is
not `main` and whose merge ref *does* carry this fix: either a new pull request opened this way after
this merges, or an existing stacked branch that has updated `main` merged or rebased into its head or
base **and receives a new push** (a retarget alone may file as `pull_request: edited`, which will not
fire a run under the default activity types). If the un-stacking policy this task adds to
`docs/DELIVERY.md` holds, a pull request stacked this way may simply not recur — in which case this
criterion stays confirmed structurally, by `actionlint`, the manual trace above, and this PR's own
live run under the unfiltered trigger (base `main`, `check` succeeded, `deploy` skipped), rather than
by a live observation on a stacked PR. That is an accepted, permanent state, not an open gap.
