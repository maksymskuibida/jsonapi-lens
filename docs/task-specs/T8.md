## Outcome

Seven defects that are live on `https://jsonapi.mstool.dev` right now stop being live. None was
introduced by this release — five were found by a baseline pass run deliberately *before* deploying,
so that the post-deploy pass could tell a regression from a pre-existing condition; two more (D6, D7)
were found afterwards, independently, while preparing this task. Fixing all seven is the maintainer's

Every one of D1–D5 was reproduced on production. D6 was reproduced locally (`LANG=de_DE.UTF-8 npx
vitest run test/crypto.test.ts`). D7 was reproduced by hand against the regex in `src/json-index.ts`.
The severities for D1–D5 are the baseline report's own; D6 and D7 are this spec's.

## D1 · Values are formatted in the browser's language, not the app's — **high**

**Observed:** with the app explicitly set to English, and again to German, dates and numbers *inside
document values* rendered in the format of `navigator.languages` — Ukrainian, on the machine that
ran the pass. Reproduced in five independent places: resource attributes, top-level `meta`, and
error `meta`. Overview stat counters are unaffected.

**Why it is worse than it looks.** `src/i18n/intl.ts` exists *specifically* to fix this, and its
header comment said so:

> Before this existed the app called `toLocaleString()` with no locale, which reads the browser's
> setting — so a German UI on an American browser rendered `1,234 Ressourcen`. Numbers now follow
> the language the user chose, like the words around them.

That was true of the catalogue's counts and false of document values, because `src/format.ts` was
never migrated: `formatDate` called `toLocaleDateString(undefined, …)` and
`toLocaleString(undefined, …)`, and `NUMBER_FORMAT` was `new Intl.NumberFormat(undefined, …)`,
constructed at **module scope** — the same trap the codebase already documents for `t()`. **So a
header comment was asserting a fix that half the app never received**, which is its own defect under
`docs/PROCESS.md` §6.

**Required:** every locale-dependent rendering of a document value goes through the chosen language.
`Intlish` in `intl.ts` is the existing home for "locale-dependent but not a translated string" —
extend it rather than adding a second mechanism. No `Intl` object is constructed at module scope. If
`intl.ts`'s header comment is still not fully true afterwards, correct the comment in the same diff.

**Resolution.** `Intlish` gained `valueNumber`/`valueDateTime`/`valueDateOnly`, and `intlFor` now
memoises its result per locale in a module-scope `Map` — populated lazily, on first call, so nothing
runs a `new Intl.…` until asked. `formatDate`/`formatNumber` in `src/format.ts` take `locale` as a
plain string parameter rather than resolving it themselves, which keeps that module pure (per
`docs/PROCESS.md` §5) — the one caller, `src/render-value.ts`, already reads `t()`/`locale()` and now
also passes `locale()` through.

## D2 · A malformed share link says "no page here" — **medium**

**Observed:** `/d/<id>:<secret>` with a secret shorter than 8 characters (tested at 7 and 5, against
a real 10) does not match `SHARE_PATTERN` at `src/router.ts`, falls through to `{ kind: "unknown" }`,
and is handled in `main.ts` by toasting *no page here* and replacing the URL with `/`.

**Correction to the baseline report**, which called this silent: it is not silent, it toasts. The
defect is that the message is **wrong**. A secret one character short matches the pattern, attempts
decryption, and correctly says the document could not be decrypted. So a link that is *slightly*
broken is diagnosed and a link that is *badly* broken is reported as a page that does not exist —
exactly backwards, and the user's next action ("was the link truncated?") is the one the message
sends them away from.

**Required:** a path shaped like a share link — `/d/<digits>` followed by anything — is recognised as
a share link. When the secret is malformed, say that the link looks truncated or damaged, name the
expected shape, and do **not** claim the page does not exist. Nothing about the accepted range for a
valid secret changes; T5 raised the practical upper bound to 64 characters and that stands.

**Do not introduce an oracle.** The new message must not distinguish "this id exists but your secret
is wrong" from "this id never existed" — that distinction is deliberately unavailable, and this
change must not leak it.

**Resolution.** `src/router.ts` exports `looksLikeShareAttempt(pathname)`, a pure shape check (a
numeric id, optionally followed by a separator and anything at all). `main.ts`'s existing call site —
`toast(t().toast.noPage(route.pathname))` — is unchanged; `noPage` itself now branches on that check
and returns the damaged-link message instead of the generic one when it applies. The router never
attempts a fetch for a share-shaped-but-malformed path either way, so the new message structurally
cannot depend on whether any particular id exists.

## D3 · `/view`'s title falls back to the paste view's whenever there is a hash — **low**

**Observed:** after following any relationship chip, or on any deep link, `<title>` and `og:title`
revert to the paste view's. `robots` and `canonical` stay correct, so this is cosmetic — but the
document title is what a browser tab and a bookmark show, and following a chip is the single most
common action in the app.

**Required:** the fragment does not change which page the head describes. `test/seo.test.ts` exists;
extend it.

**Resolution.** The actual mechanism: `main.ts#applyRoute` calls `applyRouteMeta(route)`
unconditionally on every re-entry to `/view`, including the idempotent path taken when a document is
already open and only the fragment changed (a chip click, a fragment traversal) — and
`metaForRoute`'s "view"/"share" branch used to answer with the generic app title every time, with
nothing to set the real one back on that idempotent path. `PageMeta.title`/`description` are now
`string | null`; `metaForRoute` returns `null` for "view" and "share" (routes that render somebody's
document or nothing, never a title of their own), and `applyPageMeta` leaves the title/description
already on the page alone when they are `null`. `robots`/`canonical` are keyed off `path`, not title,
and are unaffected.

## D4 · The saved-documents count goes stale on delete — **low**

**Observed:** deleting the last saved document with the modal open updates the list but leaves the
modal's subtitle count at its old value.

**Required:** the count is derived from what is rendered, not computed once when the modal opens.

**Ownership.** `src/panels.ts` is T6's file this wave. Checked `git log origin/feat/T6-share-bundle
-- src/panels.ts` and read the diff: T6's `openLibraryModal` has the identical bug (the subtitle is
still `entries.length ? … : …`, computed once, with a comment acknowledging a related-but-narrower
gap it does not close). T6 has not taken D4, so this task does.

**Resolution.** `openLibraryModal`'s `render(list)` closure now also updates `.modal__subtitle`'s
text from `list`, via the `ModalHandle.root` the real `openModal` already returns — on every call,
not only the first. No change to `src/ui.ts`.

## D5 · Strings that do not translate — **low, and non-negotiable**

**Observed** in German and Ukrainian:

- the four per-resource action buttons — *raw*, *copy*, *path*, *link* — and their tooltips;
- the **Included** overview stat label;
- the attribute-copy buttons' `aria-label`.

Visible text and `title` for the attribute-copy buttons *do* translate, so this is a partial miss
rather than a whole surface.

**Required:** every one of these comes from `en`/`de`/`uk`. An `aria-label` is user-facing copy — a
screen-reader user is a user — so it is held to the same rule as visible text: no English literal,
no fallback.

**Resolution.**

- `src/render-resource.ts#objectActions` built its four buttons from hardcoded English strings.
  `en`/`de`/`uk`'s `resource.objectActions` is a new nested group (`raw`/`rawTitle`/`copy`/
  `copyTitle`/`path`/`pathTitle`/`link`/`linkTitle`) and the function now reads from it; `title` and
  `aria-label` are the same string, as the existing local `button` helper already did for whichever
  string it was given.
- `overview.included` was the literal English word `"Included"` in **all three** catalogues,
  including `de`/`uk` — not a missing call to `t()`, a genuine untranslated row. Now `"Enthalten"`
  (de) / `"Включені"` (uk).
- `src/render-value.ts#rowActions`'s two `aria-label`s were hardcoded English strings that happened
  to equal the *English* value of the adjacent, correctly-translated `title` — `"aria-label":
  t().value.copyPointerTitle` (etc.) now reuses the same already-translated value instead of a
  second, frozen copy of it.

## D6 · `npm test` fails on a machine (or CI image) configured in German or Ukrainian — **medium**

**Observed:** `LANG=de_DE.UTF-8 LC_ALL=de_DE.UTF-8 npx vitest run test/crypto.test.ts` fails 5 of 37
tests (`LANG=uk_UA.UTF-8` fails the identical 5). Every failure is a regex asserting on English
prose — `/could not be decrypted/`, `/different version/`, `/corrupt/` — against a `ShareError`
message that came back correctly translated into German/Ukrainian instead.

**The app is not broken.** `crypto.ts` builds its error messages through `t()`, and `t()`'s
negotiation (`src/i18n/index.ts#locale`) checks `?lang=`, then a stored choice, then
`navigator.languages`, in that order. `crypto.test.ts` is `@vitest-environment node`, and Node has
shipped a real `navigator` global since v21 whose `language`/`languages` — unlike a browser's —
mirror the *host's* locale: confirmed directly, `LANG=de_DE.UTF-8 node -e
"console.log(navigator.language)"` prints `de-DE`. Nothing in the test pins a locale, so it
negotiates to whatever the machine (or CI image) is set to, and asserts English regardless. CI
passes today only because its runner's locale is `C`/`POSIX`, which happens to negotiate to `en`.

**The property to build for is not "fix three [sic — five] assertions."** It is: **a test cannot
depend on the machine's locale.** Checkable directly — identical results under `LANG=C`,
`de_DE.UTF-8` and `uk_UA.UTF-8` — and the fix has to hold for the whole suite, not just the five
currently-failing cases, since the same mechanism (any test that reaches `t()` through
`@vitest-environment node`) could recur anywhere a future node-environment test does the same thing.
`mcp/locale.ts`, on `origin/feat/T7-mcp-server`, solves the identical problem for the MCP server by
pinning `locale()`'s negotiation through `localStorage` (which takes priority over `navigator`); this
task pins the *other* end — the ambient `navigator` a test would otherwise negotiate through — since
the fix lives in `test/`, not in a long-running server process.

**Required:** `npm test` produces the same 316-then-362 results under `LANG=C`, `LANG=de_DE.UTF-8`
and `LANG=uk_UA.UTF-8`, with no test weakened to stop asserting on message content to get there.

**Out of scope:** `crypto.ts` itself, which is correct and unowned by this task; the browser suite
(`test/browser/`), which runs against a real browser rather than Node's own `navigator` and was not
observed to have this failure mode.

**Resolution.** `test/setup.ts` (a global `setupFiles` entry, already run before every test file)
now shadows `navigator.language`/`navigator.languages` to `"en-US"` with `configurable: true`. jsdom
already hardcodes these to `"en-US"` on its own, so this is a no-op for every jsdom-environment test
file; it is not a no-op for `@vitest-environment node` files, where it is the fix.

## D7 · The reference-key boundary cannot recognise a compound key in a caseless script — **low**

**Observed:** `src/json-index.ts#referenceContainerName`'s camelCase boundary —
`/^(.*[a-z0-9])(?:Id|ID)s?$/` — only ever admits `[a-z0-9]` as the character immediately before
`Id`/`ID`. A compound key such as `顧客Id` ("customer" + "Id", the way a Japanese-language payload
would spell it) can never satisfy that boundary, however naturally it reads as a reference to
someone writing that script — CJK, Kana, Hebrew, Arabic, Thai and other scripts with no upper/lower
case distinction at all are structurally excluded, not merely untested.

**Required:** the boundary also accepts a letter from a caseless script (Unicode `\p{Lo}`), and nothing
else changes about it. In particular, both properties [D4](../DECISIONS.md) already establishes must
keep holding exactly as they do today:

- `Ä` (`\p{Lu}`, upper-case) must stay **excluded** — the boundary's whole point is a character that
  is *not* upper-case, and `\p{Lo}` is the correct extension precisely because it excludes `\p{Lu}`
  and `\p{Ll}` alike; the broader `\p{L}` would not.
- `userid` (lower-case `id`, not `Id`/`ID` — no case boundary at all) must stay **unmatched**. This is
  the exact defect D4 documents fixing once already ("any key ending in the letters `id` is a
  reference"), and `\p{Lo}` must not reopen it.

**Resolution.** The regex is now `/^(.*[a-z0-9\p{Lo}])(?:Id|ID)s?$/u` (the `u` flag is required for
`\p{…}` property escapes to be recognised at all — without it the literal text `\p{Lo}` is not a
syntax error, it is silently matched as ordinary characters, which would have shipped a no-op). No
other regex in this module changes; the snake_case path (`/^(.*)[_-]ids?$/i`) already accepts any
Unicode character before its separator and was never affected by this gap.

## Error and edge cases

| Case | Expected |
|---|---|
| A date value with no time (`2026-09-02`) | Formatted in the app's language, still pinned to UTC as it was before — the existing `timeZone: "UTC"` behaviour must not change, or every date shifts by a day for some users |
| An invalid date string | Still rendered as a plain string, not as `Invalid Date` |
| A very large or non-finite number | Unchanged behaviour |
| A number with more than 6 fraction digits | Still capped at 6, as `NUMBER_FORMAT`/`valueNumber` does today |
| `/d/1:short` | Recognised as a damaged share link, with the truncation message |
| `/d/1` with no secret at all | Same message |
| `/d/notanumber:secret` | Not a share link; the existing "no page here" is correct here |
| `/d/1:valid` but the id does not exist | Unchanged: the existing gone message, indistinguishable from a wrong secret |
| A 64-character secret | Still accepted — T5 depends on this |
| `/view#r_articles__1` reloaded cold, or reached by a chip click while a document is already open | Document title, not the paste title, in both cases |
| `/view` with no hash | Unchanged |
| Deleting a non-last saved document | Count decrements correctly too, not only in the last-item case |
| Renaming a saved document | Subtitle count is unaffected (a rename does not change the count) |
| Switching language with a document open | Every fixed string changes, including the tooltips and the `aria-label`s |
| `npm test` under `LANG=C`, `de_DE.UTF-8`, `uk_UA.UTF-8` | Identical pass count and results |
| A compound key `顧客Id` (CJK) | Recognised as a reference to a `顧客` collection |
| A compound key `cafÄId` (upper-case boundary letter) | Not recognised — same as before this task |
| A bare key `userid` | Not recognised — same as before this task |
