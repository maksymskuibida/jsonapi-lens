# Task specification — T5: Storage and share envelope

> Contract level, not line level. **No UI.** This task changes what can be stored and sealed, and
> nothing about what is on screen — which is what lets T2, T6 and T7 be built in parallel on top of
> it.

## Outcome

Three things become possible without any of them breaking what exists: a saved document can carry
an attached exchange, a share link can carry one too, and **one link can carry several documents**.

The constraint that outranks all of it: **every document already in someone's IndexedDB, and every
share link already in someone's chat history, keeps working.** A stored document is somebody's work
and a share link is a promise.

## Interface

```
StoredDocument { text, savedAt, label?, exchange?: Exchange }
LibraryEntry   { id?, label, text, savedAt, bytes, resources, types, shape,
                 exchange?: Exchange }

// Sealed payloads, discriminated by the envelope's version byte.
SharePayload  { text, label, savedAt, exchange?: Exchange }      // version 2
BundlePayload { kind: "bundle", savedAt, documents: BundleEntry[] }  // version 3
BundleEntry   { label, text, exchange?, resources?, types?, shape? }
```

`Exchange` is T2's type. **T5 must not depend on T2 being finished** — declare the field as an
opaque, structurally-typed payload that T2 narrows, or import the type from a module T5 creates and
T2 fills in. Say which you did in the PR body.

## Behaviour

### IndexedDB v2 → v3

`DB_VERSION` goes to 3. `onupgradeneeded` already creates only missing stores, so the upgrade is
additive: `exchange` is a new optional property on existing records, and **a v2 record is a valid v3
record with no exchange.** No data is rewritten, nothing is migrated, and a record written by v3 and
read by a v2 build still yields its document — the extra property is simply ignored.

### The share envelope, versioned by its first byte

The envelope already carries a version byte and already refuses a version it does not know, with a
readable message. That is the mechanism to use rather than replace:

| Version | Payload | An older build reading it |
|---|---|---|
| 2 | `SharePayload` — as today, plus an optional `exchange` | Renders the document, ignores the exchange. **Graceful, and deliberate**: the document is the thing the link promised |
| 3 | `BundlePayload` | The existing "this link was made by a newer version" error, cleanly |

A single-document share therefore stays version 2 forever. **Only a bundle bumps the byte**, and it
bumps it precisely so an old client fails clearly instead of misreading a payload with no `text`.

### Bundles reuse the whole existing transport

- **No new endpoint.** A bundle is a sealed blob posted to `/api/shares` like any other. The Worker
  never learns what is inside one — that is the point of the design, and `migrations/0001_shares.sql`
  deliberately stores only id, timestamps and byte count.
- **No D1 migration.** Nothing about a bundle needs a new column.
- **No new route.** `/d/<id>:<secret>` opens either, because the decrypted payload declares its own
  kind. The alternative — a separate `/b/…` path — was rejected: the app cannot know which it has
  until it has decrypted, so a second path would be a claim the URL cannot back, and two routes to
  maintain instead of one.
- The 12 MB ciphertext cap in `src/worker.ts` applies to a bundle as a whole. Over it, the failure
  must name **which** documents made it too large and by how much, not just the total — the user's
  next action is to deselect one.

### Secrets supplied from outside

`generateSecret()` produces 10 base64url characters today. T7 will supply a 64-character hex secret
generated with `openssl rand -hex 32`, so the sealing and opening paths must accept **any** secret
in `[A-Za-z0-9_-]{8,64}`, which is exactly what `SHARE_PATTERN` in `src/router.ts` already allows.
64 characters is the pattern's upper bound, so it fits **exactly** — test the boundary, and test 65
characters being refused.

Nothing about the KDF changes: a longer secret is simply a stronger one through the same
`deriveKey(secret, salt)`.

## Error and edge cases

| Case | Expected |
|---|---|
| A v2 IndexedDB record (current document) | Opens, no exchange, nothing logged |
| A v2 library entry | Opens, listable, renamable, deletable |
| A v3 record read by a v2 build | Document renders; the extra property is ignored |
| Storage blocked entirely | Every call resolves to its safe value, as today. The app works and does not remember |
| An upgrade blocked by another tab | The existing `onblocked` rejection, and the app still works |
| A version-2 share link minted before this change | Decrypts and opens |
| A version-3 blob opened by a build that only knows 2 | The existing wrong-version error, naming both versions |
| A bundle of 1 document | **Valid, and it must not be minted** — one selected document produces a version-2 single share. A hand-made 1-entry bundle still opens |
| A bundle of 0 documents | Refused at seal time; `seal` is not the place to discover an empty selection |
| A bundle whose ciphertext exceeds 12 MB | Refused before upload, naming the largest documents and the overage |
| A bundle entry with an empty `text` | Refused at seal time — an empty document is not shareable |
| Two bundle entries with the same label | Both kept; labels are not identities |
| A bundle entry whose text is not valid JSON | Sealed and opened verbatim. The bundle is a carrier, not a validator — the reader reports the parse error per document |
| A secret of exactly 64 characters | Accepted, seals and opens |
| A secret of 65 characters, or 7 | Refused, with a message naming the bound |
| A secret that is the wrong one | The existing decryption failure, indistinguishable from a corrupt blob — do not add an oracle that tells them apart |
| A truncated or corrupt blob | The existing readable failure, never an unhandled rejection |

## Out of scope

- **All UI.** No library checkboxes, no import screen, no request form. T6 and T2 own those.
- The MCP server — T7.
- Changing the KDF, the cipher, the compression, or the version-2 payload's existing fields.
- Any new Worker endpoint, D1 column, or route.
- Server-side knowledge of bundles. The Worker must remain unable to tell a bundle from a document.

## Acceptance criteria

- [ ] A document saved by the current build opens after the upgrade, with no exchange and no error.
- [ ] A library entry saved by the current build lists, opens, renames and deletes after the upgrade.
- [ ] A share link minted by the current build still decrypts and opens.
- [ ] A version-2 payload carrying an exchange round-trips through seal and open.
- [ ] A bundle of several documents round-trips through seal and open, each entry intact byte-for-byte.
- [ ] A 64-character hex secret seals and opens; 65 and 7 are refused with the bound named.
- [ ] The Worker is unchanged, `migrations/` is unchanged, and `src/router.ts` gains no new route — or, if any of those did change, the PR body says why the design above was wrong.
- [ ] Every new user-facing string exists in `en`, `de` and `uk`, under the `bundle` catalogue namespace.
- [ ] `docs/evidence/T5.md` records that a document saved with the previous build was opened by this one — the migration is the risk, and it cannot be evidenced from unit tests alone.

## Tests that must exist

- [ ] Opening a **fixture blob sealed by the pre-change implementation** and committed to
      `test/fixtures/`. Not one sealed by your new code, which would prove only that it agrees with
      itself — this is the single test that actually protects links already in people's hands.
      **Generate it before you touch `crypto.ts`**: check the current module out to a scratch path
      (`git show main:src/crypto.ts`), seal a known payload with a known secret, commit the bytes
      and the secret as a fixture, and record in the fixture's comment which commit sealed it. A
      fixture you cannot regenerate is still valid; one generated after the change is worthless.
- [ ] A v2-shaped IndexedDB record is read by the v3 code path and yields its document.
- [ ] `seal` → `open` round-trip for: a bare document, a document with an exchange, and a bundle of three.
- [ ] A version-3 blob fed to a reader that accepts only version 2 produces the wrong-version error naming both numbers.
- [ ] Secret length: 8, 64 accepted; 7, 65 refused, each with the bound in the message.
- [ ] A wrong secret and a corrupt blob produce the **same** class of failure — asserted, so no oracle is introduced.
- [ ] An empty bundle and a bundle entry with empty text are refused at seal time.
- [ ] A bundle whose sealed size exceeds the cap is refused with the offending documents named.
- [ ] Bundle entries survive verbatim: a document containing lone surrogates, a BOM, CRLF line endings and a 5 MB single line comes back byte-identical.
- [ ] No test writes to production: the seal tests never call `fetch`.
