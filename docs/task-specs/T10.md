# Task specification — T10: The defects that only exist in the combination

> Contract level. Built on `integration/release`, which merges T5, T1, T2a, T9, T7 and T6.

## Outcome

Three defects close. None of them is visible from any single branch, and none could have been caught
by any single task's reviewer — which is the argument for having assembled the branches before the
release rather than during it.

The first is the most severe defect of the release.

---

## D-A · A secret attached through the MCP server is sealed and uploaded unredacted

**Verified, not inferred.** `redactExchange` exists in `src/secrets.ts`, is fully tested, and is
**called nowhere in the codebase.** Meanwhile `mcp/build-server.ts:173` puts a caller-supplied
`exchange` verbatim into the payload handed to `seal`/`sealBundle`, and `mcp/validate.ts` checks it
only as "any object" (`z.record(z.string(), z.unknown())`).

So an assistant using the `share` tool can attach a live `Authorization` header inside `exchange`,
and it is encrypted and uploaded to the public `/api/shares` endpoint exactly as given. That
contradicts the rule this codebase treats as non-negotiable: **a secret must not survive a share.**

**Why nobody caught it.** T2a built the redaction function and explicitly scoped itself out of
wiring it in. T6 left a comment warning that redaction must happen before an `exchange` is sealed —
resting on the premise that *nothing writes one yet*. T7 was written before T2a's real model
existed. Every one of those positions was reasonable alone. The premise became false through **T7**,
which reaches `seal` directly, bypassing `mintShareEnvelope`, `store.ts` and the browser entirely —
the one path T6's comment could not anticipate.

### What to build

**One sealing gate, and everything goes through it.** `docs/DECISIONS.md` **D3** already says a
single function decides envelope version 2 versus 3, and names T7 as a known second caller. Extend
that function's remit: **it decides the version *and* it redacts.** Then no caller can seal an
un-redacted exchange, because sealing is not something a caller does by hand.

The obstacle is real and shapes the work: `mintShareEnvelope` lives in `src/bundle.ts`, which is
browser code with DOM dependencies, and `mcp/` runs in Node. So **extract the sealing decision into
a module with no DOM** — the version choice, the redaction call, the refusals (empty bundle, empty
document, over the 12 MB cap) — and have both `src/bundle.ts` and `mcp/build-server.ts` import it.

That is a small refactor at exactly the right seam, and it is the same conclusion D3 reached for the
version byte, applied to the property that matters more.

**Redaction on this path is not optional and not offered.** In the browser, redaction is a choice
the user makes in a dialog, with a count. Through the MCP server **there is no human in the loop** —
the caller is a model, and the payload is uploaded to a public endpoint. So the gate redacts, reports
what it dropped in the tool result, and has no flag to switch it off.

### Required

- [ ] `redactExchange` is called on every path that seals an `exchange` — browser and MCP.
- [ ] A test that seals through the **MCP** path with a live-looking `Authorization` header in `exchange` and asserts the value appears **nowhere in the sealed bytes**. Assert against the bytes, not a count.
- [ ] The same for a secret in a query parameter, and one in a URL fragment.
- [ ] The MCP `share` result reports what was redacted.
- [ ] `mcp/validate.ts` validates `exchange` structurally rather than as "any object" — an unvalidated field is what let this through the type system.
- [ ] Mutation-verified: remove the redaction call and watch the byte assertion fail.

## D-B · The release branch does not typecheck

`test/bundle.test.ts` (T6's) constructs `exchange: { method: "GET" }` and `exchange: { status: 200 }`
at lines 98, 261 and 320 — T5's old flat placeholder shape. T2a's real `Exchange` requires
`{ request: { method } }` / `{ response: { status } }`. Three `TS2353` errors.

`npm test` passes because vitest does not typecheck, but the project's canonical verify chain runs
`tsc --noEmit` **first**, so this is red. A purely mechanical consequence of T6 being written against
T5's placeholder, and invisible to either branch alone.

- [ ] `npx tsc --noEmit` is clean on `integration/release`.
- [ ] The assertions still test what they tested; nesting a literal must not quietly weaken a case.

## D-C · T7 re-derives D3's decision instead of using it

`mcp/build-server.ts` branches on `documents.length === 1` against `seal`/`sealBundle` directly,
rather than going through the one function D3 designates — the exact duplication D3 was written to
prevent, in the caller D3 names by name. T7 branched before `src/bundle.ts` existed, so it had no
way to know.

**D-A's fix subsumes this**: once both callers go through the extracted gate, the duplication is gone.
Verify it actually is, rather than leaving two version decisions in the tree.

- [ ] Exactly one place in the repository decides envelope version 2 versus 3. Prove it with a search.
- [ ] `DECISIONS.md` D3 is amended to record the extraction and the added redaction remit.
