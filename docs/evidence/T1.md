## Round 2 — review fixes: what I did and what I saw

`REVIEW-PR2.md` (reviewed at `5057e37`, the round-1 head) came back with 5 blockers. I traced each
one by hand against the source before touching any code, reproduced every one exactly as reported,
fixed all five plus the two related suggestions the coordinator asked for in the same round

15. **B3 — a key merely ending in the letters `id` was read as a reference.** Pasted
    `{"valid": 1, "is_valid": true, "vals": [{"id": 1, "x": 1}, {"id": 2, "x": 2}]}` and read as plain
    JSON. Before the fix this linked `valid` straight to `/vals/0` and put a phantom `isval` chip in
    the dangling panel; after the fix, `valid` renders as an ordinary number, `is_valid` as an
    ordinary boolean, and there is no unresolved-pointers panel at all in this document.

16. **B4 — a repeated bare id-like value with nothing referencing it was reported as ambiguous.**
    Pasted `{"products": [{"code":"USD","price":1}, {"code":"USD","price":2}, {"code":"USD","price":3}]}`
    and read as plain JSON. Overview shows `ITEMS 3`, `COLLECTIONS 1`, and critically **no "Ambiguous
    identities" stat at all**. Separately re-confirmed the legitimate case still works: the step-4
    payload (`users` with two `id: 42` plus a `logs` entry that actually references `user_id: 42`)
    still shows `AMBIGUOUS IDENTITIES: 1` — the fix narrows the bug without weakening the real check.

17. **B1 — a reference past `EAGER_BODY_LIMIT` was a dead anchor.** Generated a 2,020-member `users`
    array plus `refs: [{user_id: 5}, {user_id: 2010}]` (via the browser console, since typing 2,020
    objects by hand is not a realistic QA action — see `docs/qa-notes/T1.md` step 13 for the exact
    snippet) and read as plain JSON. Inspected the rendered DOM directly:
    `user_id: 5`'s cell contains `<a class="v v--ref" href="#n__002fusers_002f5">5</a>` and that
    target exists; `user_id: 2010`'s cell contains
    `<span class="v v--ref v--ref-unrendered" title="This value is defined further down, but the
    collection is too large to show it here">2010</span>` — text, not a link — and
    `document.getElementById("n__002fusers_002f2010")` is confirmed `null`: genuinely nothing to land
    on, not merely "not clickable." The group's own note reads "20 more items not shown" (2,020 − 2,000).

18. **B2 — a resolved reference nested two or more levels deep landed on an invisible row.** Pasted
    `{"a":{"b":{"c":{"id":4}}}, "c_id":4}`, read as plain JSON, clicked the `c_id: 4` link. Before
    clicking, `b` and `c` are both closed `<details>` (only `a`, at depth 0, opens automatically).
    After clicking: both `b` and `c` are visibly expanded, `id: 4` is on screen, `location.hash` is
    `#n__002fa_002fb_002fc`, and `document.querySelector(':target')` is that same `<details>` element
    with `.open === true`. Also re-tried the milder fixture from the mutation-testing fixture
    (`{"settings":{"theme":{"id":4}}, "theme_id":4}`, one closed level rather than two) — same result,
    `theme` visibly opens on click.

19. **B5 — NDJSON could hijack a broken single document.** Pasted the comma-broken JSON:API payload
    from the review verbatim
    (`{\n  "data": [\n    {"type":"a","id":"1"}\n    {"type":"a","id":"2"}\n  ]\n}`) and clicked Read:
    got **"That is not valid JSON." / "The parser stopped here: Expected ',' or ']' after array
    element in JSON at position 44 (line 4 column 5)"** — an ordinary, accurate parse error, not a
    "This looks like JSON Lines" offer. Separately pasted the truncated-array case (`"[\n1,\n2"`):
    same outcome, "That is not valid JSON," parser error at line 3. Then re-confirmed the legitimate
    case is untouched: `{"level":"info","msg":"started"}` / `not json` / `{"level":"info","msg":"done"}`
    still reads as "This looks like JSON Lines, not JSON:API." / "Read as 2 JSON Lines records; line 2
    did not parse and was skipped." — one bad line is still tolerated; the difference is that more
    than one, or too few surviving records, no longer is.

20. **The boot/pendingOffer race (S3) — not independently reproduced live; verified by reasoning
    about the code, as documented in `docs/qa-notes/T1.md`'s Known Limitations.** The window this
    guard closes (a paste landing while `loadDocument()` is still pending) is normally too short to
    hit by clicking at ordinary speed, and there is no console-accessible hook into `boot()`'s
    internal state to force it deterministically. What I did check live: the *ordinary*, non-race
    resume path continues to work correctly after this change — saved the NDJSON document from run
    19, reloaded the whole page cold, got the "Still open: …" banner, clicked **Back to the
    document**, got the full rendered plain-JSON view, not blank. This re-confirms both the new guard
    condition and the original #27 fix (item 12 above) together, for the plain-JSON path
    specifically, which round 1 had only checked for JSON:API and one plain-JSON case via
    reload-on-`/view`.
