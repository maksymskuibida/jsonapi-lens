### N16 — `importDocuments` had no `.catch`, the same defect shape as B1

`src/bundle.ts`'s `importButton` click handler called `void importDocuments(ticked).then(outcome =>
...)` with no rejection handler — round 2 fixed the identical shape for `renderBundleImportView`
itself (B1) but missed this second occurrence twenty lines below it, flagged and left unaddressed at
N16 in the round-2 review.

`saveToLibrary` never actually rejects today (`store.ts`'s own header comment: "they resolve to a
safe value instead of rejecting"), so this cannot happen through any path reachable today — which is
exactly why it needed a test that forces it rather than one relying on an existing repro. Added
`.catch(() => renderDone({ saved: [], failedCount: attempted }, attempted))` and a test
(`test/bundle-view.test.ts`) that spies on `store.saveToLibrary` with `vi.spyOn(...).mockRejectedValue(...)`
to force exactly the rejection the fix guards against:

```
Mutation: revert the .catch (restore the bare `void importDocuments(ticked).then(...)`)
Result:   FAIL — "timed out waiting for the import to finish"
          Vitest also reports an actual Unhandled Rejection: Error: unexpected
Restored: PASS (8/8 in test/bundle-view.test.ts)
```

The unhandled-rejection message Vitest printed under the mutation is itself the concrete failure mode
this fix closes: without the `.catch`, `importButton`/`cancelButton` stay disabled forever (both were
disabled synchronously before the awaited call), `renderDone` never runs, and there is no way out of
the view — not even Cancel, which was disabled in lock-step. The acceptance criterion this closes
("Import with storage blocked -> reports that nothing could be saved rather than claiming success")
now holds on this path too, not only the one where each write individually resolves to `null`.

### N15 — `s27`'s secret sentinel made two assertions vacuous

`test/browser/nav-scenarios.js`'s `s27` extracted the secret from a freshly-minted share link with
`path.split(':')[1] || '\u0000'`. If the URL's shape ever stopped matching `/d/<id>:<secret>`, `secret`
would silently become a NUL character, and both `seen.secretGoneFromUrl` and
`seen.secretStillGoneAfterTraversals` — the assertions the scenario's own name is about — would pass
by testing for a byte that was never in the URL to begin with, rather than failing on the shape change
that produced it. This is the same class of defect the review round flagged five separate times
elsewhere in this release (per the task brief): a check that keeps reporting success after it has
stopped checking anything.

Fixed by returning a failing result instead, mirroring the sibling missing-`url` check two lines
above it. Verified by simulating exactly the failure this guards against — splitting on a delimiter
the real URL does not contain, so the extraction fails the same way a genuine shape change would:

```
Mutation: const secret = path.split('|')[1];  (was ':')
Result:   FAIL  0px  27 share a bundle, open it — Back/Forward restore paste and import
                no secret in link path /d/100001:R8gaS4hjlP
Restored: PASS (26/26 in the full run.mjs suite)
```

Under the *old* code, this identical mutation would have produced `secret = '\u0000'` and both
`secretGoneFromUrl`/`secretStillGoneAfterTraversals` would have read `true` — a false pass on a link
whose shape the scenario no longer actually understood.

### S9 — the `bundleImportEl.hasChildNodes()` guard had no test that could fail

The review confirmed this guard is real protection (it prevents a blank page on a plain F5 of a
bundle-marked `/view` entry — B1's blank page, reached a second way), but noted that deleting it left
the entire suite green: 265/265 vitest and 25/25 browser scenarios. Added a dedicated reload probe to
`test/browser/run.mjs`, placed after the existing scroll-restoration reload (so it does not need the
injected `NAV`/`SCEN` harness re-loaded after destroying the page context a second time). It
hand-stamps `history.pushState({ bundle: true }, '', '/view')` — no real share link, fetch stub or
`sealBundle` round trip needed, since the guard only ever reads `history.state` and
`bundleImportEl`'s children — reloads, and inspects the one child of `#view` that is not one of the
four static, known-by-id siblings (`bundleImportEl` itself carries no id or class; see its own
comment in `main.ts`):

```
Mutation: return state?.bundle === true;  (drop the `&& bundleImportEl.hasChildNodes()` half)
Result:   FAIL       -  a cold reload of a bundle-marked entry is not blank
                     {"path":"/view","pasteShowing":false,"docShowing":false,
                      "bundleContainerShowing":true,"bundleContainerHasChildren":false}
Restored: PASS       -  a cold reload of a bundle-marked entry is not blank
                     {"path":"/view","pasteShowing":false,"docShowing":true,
                      "bundleContainerShowing":false,"bundleContainerHasChildren":false}
```

The mutated result is the blank-page bug reproduced exactly: neither paste nor doc showing, and the
(empty) bundle container visible in their place. The restored result shows the guard correctly
falling through to the document that was actually stored (the amtrak connections document this
harness always has loaded by this point) — not a blank page, and not a resurrected bundle view either.

### S10 — the bundle marker is never cleared; the invariant that made this safe is now written down

The review judged the missing clear-on-clear harmless today, but only via an invariant nobody had
stated: every `load()` call site that shows a *different* document passes `push: true`, which is what
un-marks an entry (`router.ts`'s `navigate` puts a fresh `null` state on a push but carries the
existing state — marker included — forward untouched on a replace). This is documentation only, no
behaviour change and nothing new to test: added to `src/main.ts` at both ends of the invariant —
`isBundleEntryShowing`'s own comment (which already explained the *design* at length but never stated
what depended on it) and `LoadOptions.push`'s doc comment (the exact point where a future call site
would make the choice that could break it). Confirmed by reading: a future `load()` call added without
`push: true` on a marked entry would now find a comment explaining exactly why that inherits
`bundle: true`, at the one place such a call would be written.

### A note on the local `/api/shares` stand-in

Per this task's own brief and `docs/qa-notes/T5.md`'s precedent: `/api/*` is not served by a plain
`vite` origin. Every network call in both evidence rounds patched `window.fetch` **in the page**, for
exactly the `/api/shares`/`/api/shares/<id>` paths, backed by an in-memory `Map` — every other
request (assets, fonts) went through the real `fetch`. This exercises the entire client-side path for
real: the actual `seal`/`sealBundle`, the actual PBKDF2 derivation, the actual `open`/
`isBundlePayload`, the actual DOM. Only the two HTTP round trips to a real Worker are stand-ins. To
open a resulting link without a full page reload (which would discard the in-page patch and make the
GET fail for real), the id/secret were read out of the created link and applied via
`history.pushState` plus a synthetic `popstate` event — the same event the browser's own Back/Forward
dispatches, which is what lets `main.ts`'s real, unmodified `popstate` listener run rather than being
simulated itself.
