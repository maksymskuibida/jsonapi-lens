## Why this ran on a hand-started server rather than `preview_start`

`preview_start` in this session is bound to a different worktree
(`.claude/worktrees/json-jsonapi-request-support-e56641`, confirmed via `preview_list`'s `cwd`, and
independently confirmed by fetching `/src/main.ts` from it and finding none of this task's new code)
— it is the orchestrator's own checkout for a separate, unrelated task, not this worktree
(`agent-a0850b5a0afe028cd`, branch `feat/T6-share-bundle`). Stopping and restarting it under a new
name still returned the same, wrongly-rooted server: this is a hard binding for a spawned subagent in
an isolated worktree, not something a differently-named `.claude/launch.json` entry could route
around (that entry was added, used, then reverted — it is not part of this diff). Rather than risk
disrupting whatever else depends on that shared server, or move this session's directory (a
heavyweight, user-facing operation inappropriate for a spawned implementer), this evidence was
gathered against a `vite` instance started from this worktree on its own port, and interacted with
entirely through the same browser-pane tool (`navigate`, `computer`, `read_page`,
`javascript_tool`) — every action below is a real browser doing real DOM work against real,
this-worktree code; only the *origin* differs from the usual `preview_start` flow. Both ad-hoc
servers were stopped, and `.claude/launch.json` was left exactly as this branch found it.

## A note on the local `/api/shares` stand-in

Per this task's own brief and `docs/qa-notes/T5.md`'s precedent: `/api/*` is not served by a plain
`vite` origin. Steps 7–14 above patched `window.fetch` **in the page**, for exactly the
`/api/shares`/`/api/shares/<id>` paths, backed by an in-memory `Map` — every other request (assets,
fonts) went through the real `fetch`. This exercises the entire client-side path for real: the actual
`seal`/`sealBundle`, the actual PBKDF2 derivation (the multi-second delay was genuinely paid, not
skipped), the actual `open`/`isBundlePayload`, the actual DOM. Only the two HTTP round trips to a real
Worker are stand-ins. To open the resulting link without a full page reload (which would have
discarded the in-page patch and made the GET fail for real, since nothing on this dev origin serves
it), the id/secret were read out of the created link and applied via `history.pushState` plus a
synthetic `popstate` event — the same event the browser's own Back/Forward dispatches, which is what
lets `main.ts`'s existing, unmodified `popstate` listener run for real rather than being simulated
itself.

## NOT OBSERVED

- **A real bundle uploaded to and fetched from the actual Cloudflare Worker.** Every network call in
  this evidence was intercepted in-page; the real `/api/shares` endpoint was never hit. This is the
  same gap `docs/qa-notes/T5.md` left open for the single-document path, now equally open for the
  bundle path — it needs either a production pass (this profile does not have a pre-production
  environment yet) or `wrangler dev` run locally, neither of which this task performed. **Do not read
  the local pass above as proof the Worker round-trips a bundle correctly** — it proves the client
  does, which is everything this task owns.
- **A version-3 link opened by a genuinely older, unmodified build.** T5's own evidence/tests cover
  the wrong-version error in the abstract (a version byte this build does not expect); this task did
  not additionally install a pre-T5 build somewhere to open a live bundle link with it. Not expected
  to differ from what T5 already verified, since T6 does not touch the version-check code path at all.
- **Keyboard-only traversal of the whole selection flow**, timed and screen-reader-verified. Confirmed
  the checkboxes carry correct accessible names (via the accessibility tree) and that focus lands
  sensibly after mode transitions (read from source and confirmed the DOM order supports native Tab
  flow), but did not drive the entire flow with a physical/virtual keyboard end to end, nor with an
  actual screen reader.
- **50 documents in one bundle**, rendered and scrolled. Confirmed the CSS (`max-height` +
  `overflow: auto` on `.bundle-import__list`) with 2 rows and by reading the rule; did not construct
  a 50-entry bundle to watch the internal scrollbar appear.
- **Redaction interacting with a bundle.** Not built anywhere in this codebase yet (T2) — nothing to
  observe.
