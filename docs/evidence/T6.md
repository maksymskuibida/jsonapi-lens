### B1 — a hostile link produced a blank page with no error

Reproduced the reviewer's exact attack shape live, using this build's own `crypto.ts` via a dynamic
`import('/src/crypto.ts')` from the console (the same module the app itself loads — not a
reimplementation):

```js
const secret = generateSecret();
const hostile = { text: '{}', label: 'l', savedAt: 1, kind: 'bundle' }; // valid v2 SharePayload + an extra field
const blob = await seal(hostile, secret); // blob[0] === 2 — genuinely version 2
```

Served that blob from a stubbed `/api/shares/777`, opened `/d/777:<secret>` via `history.pushState` +
a synthetic `popstate` (see the note on this technique, preserved below), and observed:

```json
{
  "path": "/",
  "errorShown": true,
  "errorHeadline": "That shared bundle is corrupt.",
  "errorHint": "It decrypted, but does not contain a bundle.",
  "pasteHidden": false,
  "bundleContentExists": false
}
```

The paste view with a readable error, not a blank page. Screenshot taken; matches. This is
`isWellFormedBundlePayload` (new, `src/bundle.ts`) rejecting the payload before
`payload.documents.map` is ever reached, and `loadSharedDocument` now `await`ing
`renderBundleImportView` so the existing `catch` block is what actually runs.

### S3, escalated to a blocker — the sticky flag leaked into an unrelated navigation

Reproduced the reviewer's exact five-step repro live, against this commit, end to end through the
real UI (a real bundle link, minted and opened with the same in-page `fetch` stub technique used
throughout this file):

```json
{
  "step1": { "path": "/view", "importShowing": true },
  "step2": { "path": "/", "pasteHidden": false },
  "step3": { "path": "/view", "docHidden": false },
  "step4": { "path": "/" },
  "step5": {
    "path": "/",
    "importShowingStale": false,
    "docHidden": true,
    "pasteHidden": false,
    "bodyTextSnippet": "jsonapi·lens\nSaved\n?\nLanguage\nEN\nDE\nUK\nauto\n\nJSON:API DOCUMENT VIEWER\n\nFollow the pointer…"
```

Step 5 is the repro's own final assertion: bundle → Cancel → paste → paste a document → **New

what the extended `s27` scenario now asserts automatically (`leakCheckBackDoesNotShowImportView`),

to a plain sticky flag and watching that exact assertion go red, then green again after reverting.

### A note on the local `/api/shares` stand-in

Per this task's own brief and `docs/qa-notes/T5.md`'s precedent: `/api/*` is not served by a plain
`vite` origin. Every network call in both evidence rounds patched `window.fetch` **in the page**, for
exactly the `/api/shares`/`/api/shares/<id>` paths, backed by an in-memory `Map` — every other
request (assets, fonts) went through the real `fetch`. This exercises the entire client-side path for
real: the actual `seal`/`sealBundle`, the actual PBKDF2 derivation, the actual `open`/
`isBundlePayload`, the actual DOM. Only the two HTTP round trips to a real Worker are stand-ins. To
open a resulting link without a full page reload (which would discard the in-page patch and make the
GET fail for real), the id/secret were read out of the created link and applied via
`history.pushState` plus a synthetic `popstate` event — the same event the browser's own Back/Forward
dispatches, which is what lets `main.ts`'s real, unmodified `popstate` listener run rather than being
simulated itself.

## NOT OBSERVED

- **A real bundle uploaded to and fetched from the actual Cloudflare Worker.** Every network call in
  this evidence was intercepted in-page; the real `/api/shares` endpoint was never hit. Needs either a
  production pass (this profile does not have a pre-production environment yet) or `wrangler dev` run
  locally, neither of which this task performed. **Do not read the local passes above as proof the
  Worker round-trips a bundle correctly** — they prove the client does, which is everything this task
  owns.
- **A version-3 link opened by a genuinely older, unmodified build.** T5's own evidence/tests cover
  the wrong-version error in the abstract; this task does not touch that code path and did not
  additionally install a pre-T5 build to open a live bundle link with it.
- **Keyboard-only traversal of the whole selection flow, timed and screen-reader-verified.**
  `test/panels.test.ts` and this round's live session both confirm focus lands correctly *entering*
  selection mode (B2's fix) — genuinely observed now, not merely asserted by source-reading, as the
  previous round's NOT OBSERVED section for this had to admit. What is still not driven end to end is
  Tab moving between the remaining checkboxes, Space toggling, and reaching `Create link`, with a
  physical or virtual keyboard the whole way through, or with an actual screen reader. `docs/
  test-plans/T6.md` rows 28/28a and `docs/qa-notes/T6.md`'s Known Limitations now say this plainly
  rather than claiming it was satisfied.
- **Redaction interacting with a bundle.** Not built anywhere in this codebase yet (T2) — nothing to
  observe. `docs/DECISIONS.md` D3 and `src/bundle.ts` both carry the warning for when it is.
