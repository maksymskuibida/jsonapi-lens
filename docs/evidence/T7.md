## What I did and what I saw

1. Ran `client.listTools()` against the real server over a real `StdioClientTransport` (a one-off
   script, not committed — see "How this was actually run" below). Both `share` and `read` are
   registered; `share`'s description is 647 characters, `read`'s 562.

2. Called `share` with one synthetic document (`t7-evidence.json`, a 2-resource JSON:API payload,
   292 bytes of plaintext) and a real `openssl rand -hex 32` secret, against
   `https://jsonapi.mstool.dev` with `lifetime: "15m"` → got back
   `{ id: 15, url: "https://jsonapi.mstool.dev/d/15:70d09e...b1af8", expiresAt: 1788394325305,
   bytes: 299, kind: "document" }`. The `content` text field read "Shared 1 document as a document
   link (id 15, 299 bytes). The link, with the secret, is in this result's `url` field." — no secret
   in it.

3. Called `read` with that same id and secret, same origin → got back `{ kind: "document", label:
   "t7-evidence.json", savedAt: 1788393424589, text: "<the exact JSON I sent>" }`. Compared the
   `text` field to the original string: identical, character for character.

4. **Opened the `url` from step 2 in a real browser tab, against production, unmodified.** The
   address bar settled on `https://jsonapi.mstool.dev/view` (confirmed via
   `location.href`/`location.pathname` in the page's own console — the secret and id are gone from
   the address bar, exactly as the existing share-link behaviour promises). The page title read
   `t7-evidence.json — jsonapi-lens`. The rendered document showed exactly what was shared: `SHAPE
   data[2]`, `RESOURCES 2`, `TYPES 1`, `SIZE 292 B`, and under Primary Data, two `articles`
   resources whose `TITLE` fields read "T7 evidence — synthetic, safe to expire" and "Second
   synthetic article" — the two attribute values from the document I passed to `share`. **This is
   the acceptance criterion "`share` with one document returns an id and a URL that opens in a
   browser and renders the document" and "a link minted by `share` is readable by the browser",
   verified against the real, deployed site, not a simulation of it.**

5. Console for that page load: one `[info] [jsonapi-lens] timings {resources: 2, types: 1, bytes:
   292, …}` line (the app's own normal instrumentation) and one unrelated `[error] Failed to load
   resource: the server responded with a status of 410 ()`. Investigated the second one:
   `read_network_requests` for this page load shows every request succeeding (`200`/`200
   OK`/`304 Not Modified`) — the share fetch itself (`GET /api/shares/15`) returned `200`, and
   nothing in the request log for this navigation is a `410`. This browser tab had earlier, unrelated
   activity in it from before this evidence run (a `localhost:5179` dev-server preview from earlier
   in this session, visible in the same network log, on a different origin). Recording this rather
   than silently dropping it: the 410 did **not** correspond to any request this evidence run made,
   and did not affect the render — but it is exactly the kind of loose end that gets marked NOT
   OBSERVED rather than waved away.

6. Called `share` again with **three** synthetic documents and a second fresh secret, same origin,
   same 15-minute lifetime → got back `{ id: 16, url: "…/d/16:50b0a0…58f5bdb", bytes: 294, kind:
   "bundle" }`. Called `read` with that id and secret → got back `{ kind: "bundle", savedAt: …,
   documents: [ {label: "t7-evidence-bundle-1.json", text: "…"}, {label:
   "t7-evidence-bundle-2.json", text: "…"}, {label: "t7-evidence-bundle-3.json", text: "…"} ] }` —
   all three present, in the order they were sent, each `text` field matching what was sent exactly.
   **This is the acceptance criterion "`read` returns the text byte-for-byte as it was passed to
   `share`" and "`read` of a bundle: `kind: "bundle"` with every entry", verified against production
   for a real, network-round-tripped bundle** (not just this repo's in-memory test stub).

7. **Opened the bundle's `url` from step 6 in the browser, against production.** It rendered the
   ordinary paste screen with: "That share link was made by a different version. It uses format
   version 3, and this build reads version 2. Ask for a fresh link." This is **expected, correct,
   and not a defect**: `main` (what production currently runs) predates T5, which has not merged
   yet, so the deployed build genuinely only knows version 2. What this actually demonstrates is two
   things at once — the bundle really was sealed at envelope version 3 (an independent, unmodified
   reader identified it as exactly that), and the existing wrong-version error still fires cleanly
   for it rather than the page crashing or silently misreading a bundle as an empty document. See
   "NOT OBSERVED" for what this run could not show as a result.

8. Grepped every value returned across both runs (`listTools`, both `share` results, both `read`
   results) for either secret used, with each result's own `url` field removed first: no match in
   either case. Grepped the subprocess's captured stderr (`jsonapi-lens MCP server ready on
   stdio.` was the only line) for either secret: no match. This is the same check
   `test/mcp/e2e-subprocess.test.ts` makes automatically, repeated here against production rather
   than a loopback stub.

## How this was actually run

Two short Node scripts (not committed — they existed only in the repository root for the duration of
each run, then were deleted; `git status` was clean before and after each), each spawning
`mcp/server.ts` via `node_modules/.bin/tsx` exactly as `mcp/README.md`'s registration example does,
using the SDK's own `Client`/`StdioClientTransport` to speak real stdio to it — the same mechanism
`test/mcp/e2e-subprocess.test.ts` uses, run here against `https://jsonapi.mstool.dev` instead of a
loopback stub. Both secrets were generated with the literal `openssl rand -hex 32` this task's own
tool description tells a caller to run, written to a temp file, read back and validated as 64
lowercase hex before use, and are not reproduced in this file — see "Secrecy" below.

## Failure paths I triggered

Not part of this specific run — every refusal case in `docs/task-specs/T7.md`'s table (bad secret,
bad lifetime, bad origin, empty documents, oversized documents, 404, 410, wrong secret, wrong
version) is covered by `test/mcp/tools.test.ts` and `test/mcp/transport.test.ts`, each confirmed
capable of failing (see `docs/test-plans/T7.md`'s note on the size-cap tests specifically). This
evidence run's job was the one thing those tests cannot prove by construction — that the real,
deployed site actually opens what this server actually uploads, and vice versa for the version
mismatch — so it stuck to the happy paths plus the one genuinely-expected "different version"
outcome.

## Secrecy

Both secrets used in this run were generated fresh with `openssl rand -hex 32`, used only against
the synthetic documents above, and are not written anywhere in this repository, this file, or any
commit. The shares they protect expire in 15 minutes from creation (`2026-09-03`, around the time
this file was written) and are not needed again — nobody, including a future reader of this file,
needs either secret to understand what was verified.

## NOT OBSERVED

  documents returns a URL that opens the bundle import view with all three" cannot be observed by
  anyone right now, by any means: that view is T6's, not built yet in any branch, and would need
  T5 merged first regardless. What step 7 above verified instead — the closest available substitute
  — is that a bundle this server mints is genuinely sealed at version 3 (an unmodified reader
  identifies it as such) and fails exactly the way `docs/task-specs/T5.md` promises a build that
  only knows version 2 will. Re-run this file's step 7 once T5 has merged and T6 has shipped its
  view, and record what actually renders.
- **The stray `410` console message in step 5.** Investigated as far as this run's own network log
  goes (no matching failed request), but not traced to a definite cause — most likely unrelated
  browser-tab history from earlier, unconnected work in this session. Flagged rather than dismissed.
- **A self-hosted fork, or any `origin` other than the production default.** `mcp/validate.ts`
  accepts an explicit `http://` origin and `test/mcp/validate.test.ts` covers that structurally, but
  this evidence run only exercised the real default origin — there was no second deployment to point
  it at.

  pure function in `test/mcp/runtime.test.ts` (every combination of version and missing
