## What I did and what I saw

1. Ran `client.listTools()` against the real server over a real `StdioClientTransport` (a one-off
   script, not committed — see "How this was actually run" below). Both `share` and `read` are
   registered.

2. Called `share` with one synthetic document (`t7-evidence-2.json`, a 2-resource JSON:API payload)
   and a real `openssl rand -hex 32` secret, against `https://jsonapi.mstool.dev` with `lifetime:
   "15m"` → got back `{ id: 17, url: "https://jsonapi.mstool.dev/d/17:31cf8b…6fc60", expiresAt:
   1788395126143, bytes: 298, kind: "document" }`. The `content` text field read "Shared 1 document
   as a document link (id 17, 298 bytes). The link, with the secret, is in this result's `url`
   field." — no secret in it.

3. Called `read` with that same id and secret, same origin → got back `{ kind: "document", label:
   "t7-evidence-2.json", savedAt: 1788394225685, text: "<the exact JSON I sent>" }`. Compared the
   `text` field to the original string: identical, character for character.

4. **Opened the `url` from step 2 in a real browser tab, against production, unmodified.** The
   address bar settled on `https://jsonapi.mstool.dev/view` (confirmed via
   `location.href`/`location.pathname` in the page's own console — the secret and id are gone from
   the address bar). The page title read `t7-evidence-2.json — jsonapi-lens`. The rendered document
   showed exactly what was shared: `SHAPE data[2]`, `RESOURCES 2`, `TYPES 1`, `SIZE 293 B`, and under
   Primary Data, two `articles` resources whose `TITLE` fields read "T7 evidence rerun — synthetic,
   safe to expire" and "Second synthetic article, rerun" — the two attribute values from the document
   passed to `share`. **This is the acceptance criterion "`share` with one document returns an id and
   a URL that opens in a browser and renders the document" and "a link minted by `share` is readable
   by the browser", verified against the real, deployed site.**

5. Console for that page load, read after both this and the earlier (now-stale) run had used the same
   tab: two `[info] [jsonapi-lens] timings …` lines, one per page load (`bytes: 292` and `bytes: 293`
   respectively, matching each run's own document size), and one `[error] Failed to load resource:
   the server responded with a status of 410 ()`. `read_network_requests` for the whole tab's history
   across both runs shows every request succeeding — `200`, `304 Not Modified`, nothing else — across
   all three share ids fetched in this session (`15`, `16` from the earlier run, `17` from this one).
   The `410` does not correspond to any request in that log.
   **Resolved on review, closed:** a `410` can only come from one place in this system —
   `GET /api/shares/<expired id>` — and this browser tab, across both the original and the re-run
   evidence pass, created three 15-minute shares over roughly 20-25 minutes of session time. Chrome
   preserves the console panel's log across page loads within a tab; the network panel's log is
   per-document and does not. So a console `410` with no matching request in a *later* page load's
   network log is exactly what an earlier pass's share re-fetching after its own 15 minutes elapsed
   would produce — no new mechanism needed, and consistent with every other fact this file records.
   Not independently re-verified beyond that reasoning, but treated as closed rather than reopened
   with each future evidence run.

6. Called `share` again with **three** synthetic documents and a second fresh secret, same origin,
   same 15-minute lifetime → got back `{ id: 18, url: "…/d/18:a415b5…9c770", bytes: 300, kind:
   "bundle" }`. Called `read` with that id and secret → got back `{ kind: "bundle", savedAt: …,
   documents: [ {label: "t7-evidence-bundle-1-rerun.json", text: "…"},
   {label: "t7-evidence-bundle-2-rerun.json", text: "…"},
   {label: "t7-evidence-bundle-3-rerun.json", text: "…"} ] }` — all three present, in the order sent,
   each `text` matching exactly. **This is the acceptance criterion "`read` returns the text
   byte-for-byte as it was passed to `share`" and "`read` of a bundle: `kind: "bundle"` with every
   entry", verified against production for a real, network-round-tripped bundle** (not just this
   repo's in-memory test stub).

7. **Opened the bundle's `url` from step 6 in the browser, against production.** It rendered the
   ordinary paste screen with: "That share link was made by a different version. It uses format
   version 3, and this build reads version 2. Ask for a fresh link." **Expected and correct**:
   `main` (what production currently runs) predates T5, which has not merged yet, so the deployed
   build genuinely only knows version 2. This demonstrates the bundle really was sealed at envelope
   version 3 (an independent, unmodified reader identified it as exactly that) and that the existing
   wrong-version error still fires cleanly for it. See "NOT OBSERVED" for what this could not show.

8. Grepped every value returned across both runs (`listTools`, both `share` results, both `read`
   results) for either secret used, with each result's own `url` field removed first: no match in
   either case. Grepped the subprocess's captured stderr (`jsonapi-lens MCP server ready on
   stdio.` was the only line, for each run) for either secret: no match. This is the same check
   `test/mcp/e2e-subprocess.test.ts` makes automatically, repeated here against production.

9. **B1 — the one the first review round found: a real link minted by the real Share button, read
   by this server.** In a real browser tab against production, pasted a third synthetic document
   (`{"data":[{"type":"articles","id":"b1","attributes":{"title":"B1 real-browser evidence,
   synthetic, safe to expire"}}], "meta": {"note": "Minted by the real Share button, read back by
   the MCP server, for T7 evidence."}}`), clicked the page's own **Share link** button (not this
   server, not a script — the actual UI control), chose 15 minutes, and clicked **Create link**.
   The modal showed a link at id `19` whose secret had exactly `generateSecret()`'s real shape — 10
   mixed-case letters and digits, e.g. the shape `Ab3d_f8Xy1` (illustrative, not the actual value) —
   nothing like the 64-hex `share` mints. Read the exact value back from the modal's own input
   element (`document.querySelector('input[readonly]').value`) rather than transcribing the
   screenshot, to rule out misreading a `0`/`O` or `l`/`1`/`I` — a misread character would have
   produced a decryption failure indistinguishable from a policy refusal, and this step would have
   "passed" for the wrong reason. Called this server's `read` tool with that id and secret against
   production → got back `{ kind: "document", label: "pasted document", text: "<the exact JSON
   pasted into the browser>" }`, byte-for-byte identical, and the secret did not appear in the
   subprocess's captured stderr. **This is the acceptance criterion "a link minted in the browser is
   readable by `read`" verified with an actual browser-generated secret, not `generateSecret()`
   called from a script** — the gap the first review round found and `mcp/validate.ts`'s
   `assertReadSecret` now fixes. The share itself expired (15-minute lifetime) hours before this
   sentence was revised to remove the literal value; removed for hygiene, not because the value was
   ever exploitable after that point.

## How this was actually run

Three short Node scripts (not committed — each existed only in the repository root for the
duration of its own run, then was deleted; `git status` was clean before and after every run), each
spawning `mcp/server.ts` via `node_modules/.bin/tsx` exactly as `mcp/README.md`'s registration
example does, using the SDK's own `Client`/`StdioClientTransport` to speak real stdio to it — the
same mechanism `test/mcp/e2e-subprocess.test.ts` uses, run here against
`https://jsonapi.mstool.dev` instead of a loopback stub. Steps 1-8's four secrets were each
generated with the literal `openssl rand -hex 32` this task's own tool description tells a caller
to run, written to a temp file, read back and validated as 64 lowercase hex before use. Step 9's
secret was not generated by any script at all — it is `generateSecret()`'s real output, produced by
an actual click on the deployed site's own Share button, read back from the modal's own DOM element.
None of the five secrets are reproduced in this file — see "Secrecy" below.

## Failure paths I triggered

Not part of this specific run — every refusal case in `docs/task-specs/T7.md`'s table (bad secret,
bad lifetime, bad origin, empty documents, oversized documents, 404, 410, wrong secret, wrong
version) is covered by `test/mcp/tools.test.ts` and `test/mcp/transport.test.ts`, each confirmed
capable of failing (see `docs/test-plans/T7.md`'s note on the size-cap tests, and this PR's own
description for the mutation tests run against `mcp/build-server.ts` before opening it). This
evidence run's job was the one thing those tests cannot prove by construction — that the real,
deployed site actually opens what this server actually uploads, and vice versa for the version
mismatch — so it stuck to the happy paths plus the one genuinely-expected "different version"
outcome.

## Secrecy

Four of the five secrets used across this run were generated fresh with `openssl rand -hex 32`; the
fifth (step 9) is the deployed site's own `generateSecret()` output, produced by one real click on
its Share button. All five were used only against the synthetic documents above, and none are
written anywhere in this repository, this file, or any commit. Every share they protect used the
15-minute lifetime and is not needed again — nobody, including a future reader of this file, needs
any of them to understand what was verified.

## NOT OBSERVED

- **The bundle-import view.** `docs/task-specs/T7.md`'s acceptance criterion "`share` with three
  documents returns a URL that opens the bundle import view with all three" cannot be observed by
  anyone right now, by any means: that view is T6's, not built yet in any branch, and would need
  T5 merged first regardless. What step 7 above verified instead — the closest available substitute
  — is that a bundle this server mints is genuinely sealed at version 3 (an unmodified reader
  identifies it as such) and fails exactly the way `docs/task-specs/T5.md` promises a build that
  only knows version 2 will. Re-run this file's step 7 once T5 has merged and T6 has shipped its
  view, and record what actually renders.
- **A self-hosted fork, or any `origin` other than the production default.** `mcp/validate.ts`
  accepts an explicit `http://` origin and `test/mcp/validate.test.ts` covers that structurally, but
  this evidence run only exercised the real default origin — there was no second deployment to point
  it at.
- **An actually-too-old Node.** `mcp/runtime.ts`'s `runtimeProblem` is exercised exhaustively as a
  pure function in `test/mcp/runtime.test.ts` (every combination of version and missing
  capabilities), but this evidence run — like that test file — did not install an older Node
  binary and run the real entry point against it. The pure-function tests are the intended substitute
  for that, per `docs/test-plans/T7.md`.
- **The locale pin, under a real MCP client rather than this project's own subprocess harness.**
  `test/mcp/locale-pin.test.ts` and manual verification during the first review's fix round both
  confirm the pin holds when spawned directly with a hostile `LANG`; neither exercises an actual
  third-party MCP host (Claude Desktop or similar) configured with a non-English system locale.
- **Every one of the documented refusal messages, read by a human rather than asserted by a test.**
  Spot-checked several while writing `mcp/validate.ts` and `mcp/transport.ts`, but did not
  re-transcribe all of them into this file; `docs/test-plans/T7.md` and `test/mcp/` are the record
  for those.
